> the human approves.

## 0. The hard constraint (read before proposing anything)

The owner's instruction, verbatim in intent:

> **절대 만들고자 하는 목적 이상으로 불필요한 검증 게이트나, 보안 등으로 프로젝트 규모를 확장하지 말 것.**
> Never expand the project's scope beyond its purpose by adding verification gates, security layers,
> or ceremony.

This is a **binding constraint on the debate output**, not a preference. Concretely, a proposal is
out of bounds if it:

- adds a new gate whose purpose is to prove the harness did not bypass its own gates;
- adds a security control not motivated by a threat this repo actually faces (a solo-owned,
  private-ish monorepo with a reviewed-by-merge model);
- adds a human-must-**author** step (as distinct from human-must-**review**) anywhere;
- introduces a second control plane over something an existing plane already covers;
- grows the artifact surface (commands / skills / agents / contracts / CI jobs) without retiring at
  least as much, unless the addition directly serves one of the four goal functions in §2.

**Default answer to "should we also gate X?" is NO.** The burden of proof is on the addition.

## 2. The owner's actual goal (restated, authoritative)

> A **monorepo** holding several related, closely-coupled projects. Keep each project's
> **conventions** and their **interface-contract relationships** consistent. Make an **LLM working
> in the repo understand cross-project relationships better than it would in a generic repo.**
> Nothing more. Development speed matters; ceremony that a human must personally perform (beyond
> reviewing) does not serve the goal.

Four goal functions follow. Every proposal must map to at least one.

| # | Goal function | Present coverage | Gap |
|---|---|---|---|
**①** | Convention consistency across packages | language lint/format adapters, nearest-wins `AGENTS.md`, single-source emit | convention *profile* is not per-package/inherited data |
**②** | Interface contracts between packages | `contracts/` single source, JCS schema-hash drift gate, relationship graph | contracts are a flat global list, not attributed to graph **edges** |
**③** | LLM comprehension of cross-project relationships | repo-map (tree-sitter + PageRank), contracts-index, SessionStart injection, graph queries | **topology is hand-declared**, and **impact analysis is buried inside a gate instead of exposed as a dev affordance** |
**④** | Long-horizon maintainability | append-only ADR, auto-regenerated derived plane, CI-strong posture (ADR-0011) | no **allowed-dependency rule** as data; no **install/upgrade path** into another monorepo |

Note what is *not* a goal: proving the harness cannot be bypassed; achieving a defensible security
posture; modelling task lifecycle in a schema-verified state machine.

## 3. Diagnosis

ADR-0011 already states the mechanism: *every milestone's subject matter **is** gate machinery, so
"maintain consistency" drifted into "add more gates."* Its prescription, however, covers only the
in-session hot path (`HARNESS_DEV_LIGHT` + infrastructure degrade). The diagnosis is repo-wide; the
remedy was one layer. Three consequences:

1. **Ceremony concentration.** The v2.2 task-control plane plus v2.4 Theme C — 8 `tools/` packages,
   7 contracts, 4 commands, 5 skills, 1 CI job, 1 hook — models a task lifecycle with lanes,
   disciplines, evidence bundles, CAS, attestations, handoff schemas and shadow metrics. It maps to
   **none** of ①②③④. GSD already governs lifecycle, so this is a second control plane over the same
   thing — and the owner reports it is too heavy for the in-house model to drive.
2. **Self-verification mass.** A large share of the ~40k LOC in `tools/` verifies the harness rather
   than serving the four goal functions. Phase 30's remaining plans would add more of exactly this.
3. **The instance is a toy.** `examples/log-parser/` is the only instance and its converter is a toy,
   so nothing demonstrates the harness against a real multi-project monorepo. ADR-0002's
   template/instance split is sound; the instance side just never got built out.

## 4. Proposal

### 4.1 Lightweight lifecycle — adopt the vendored `opencode-matt-workflows` pattern

Already vendored at `docs/references/opencode-matt-workflows/` (excluded from ruff in phase 34).
Contents: a `flow-router`, 27 `flow-*` agents (`small-change · bugfix · feature · prototype ·
research(-plan) · architecture(-scan/-plan) · ticket · triage · conflicts · large-project` + 9
adversarial roles), 19 commands, and `WORKFLOW_CONTRACTS.md` defining three **text** contracts
(router handoff / direct command / agent completion: `Outcome · Artifacts · Verification · Decisions ·
Risks · Next command`). Methodology is delegated to Matt Pocock's upstream skills via
`npx skills@latest add mattpocock/skills` — the wrappers deliberately do not copy or summarize the
upstream instructions, and that boundary must be preserved (`UPSTREAM_SKILLS.md`,
`THIRD_PARTY_NOTICES.md`).

One-to-one replacement of the heavy plane:

| Current (heavy) | Replacement |
|---|---|
`tools/risk_router` 7-axis scoring + policy router | `flow-router` — route by request shape |
lane × required-artifact matrix, `tools/discipline`, `tools/capability` allowlist | one `flow-*` agent per route; upstream skills carry the methodology |
`handoff.schema.json`, `evidence.schema.json`, CAS, `attestation.schema.json` | the three text contracts (no schema, no content-addressed store) |
`transitions.json` state machine, `phase-gate`, `resume_gate` hook | `flow-progress`, `flow-feature-resume` |
`adversarial-review-panel` skill + STRICT+ lane requirement | `flow-adversarial-*`, invoked on demand, never mandatory |
`tools/lifecycle_eval` + CI job | nothing |

Why this suits a weaker in-house model: the only judgment call is *which route*. Everything after is
a fixed procedure in one document with an explicit stop condition and completion contract. No 7-axis
scoring, no evidence-bundle assembly, no state-machine reasoning.

**What the harness adds on top — and this is the whole differentiator.** Matt's flows are
repo-agnostic. Each flow's *Repository evidence* section gets injected with monorepo facts this
harness alone can compute: the impact set for the touched paths, the affected interface contracts,
any allowed-dependency violations, and the package sub-graph. Same flows, monorepo-aware.

**Residual to keep:** `tools/task_control` shrinks to one minimal state file that `flow-progress`
reads (current route · step · next command). State machine, CAS and attestation removed.

### 4.2 `harness-author` — a Q&A skill that generates monorepo-specific artifacts

The template's missing piece: the harness should be able to author *this monorepo's* agents, skills,
commands and flows, without the human having to specify them cold.

Mechanism — **evidence first, then interview:**

1. The skill scans the repo before asking anything: package graph, manifests, `contracts/`, doc tree
   (Diátaxis quadrants), existing agents/skills/commands, dependency edges, test layout.
2. It proposes **grounded defaults** with citations (`path:line`), and the human answers by
   confirming or correcting — never by authoring from scratch.
3. Slots to converge, one question at a time:
   - **purpose + route condition** — which requests should reach this artifact
   - **authority level** — read-only / propose / implement / implement-and-merge
   - **required reading** — which documents and contracts, proposed from the codebase
   - **guidance and prohibitions**
   - **least-privilege tools** — tool set and bash scope
   - **completion contract** — reuse Matt's agent completion contract
   - **anti-sprawl** — "why is this not an extension of an existing artifact?" (absorbed from the
     current `skill-creator`, whose anti-sprawl question is preserved)
4. Output is written to the runtime-neutral `harness/{agents,skills,commands}/`, so the existing
   emitter projects it to both `.opencode/` and `.claude/`, existing cap validation applies
   (`name` ≤ 64, `description` ≤ 1024, body length, permission keys, no real model IDs), and
   `registry.lock` plus the router's route table update.

`skill-creator` is absorbed into this skill rather than kept alongside it.

#### Accepted trade-off, stated plainly

Enforcement collapses onto CI plus the merge decision. If the owner does not actually read the PR,
there is no second net. Under solo ownership that is already true — today's human-must-author gates
are self-signed, so they are cost without protection. Every deletion is recoverable from git.

## 5. Questions the debate must settle

1. **Command budget.** Importing 19 `flow-*` commands while deleting 6 grows the surface. Import all
   19, a subset (`small-change · bugfix · feature · research · review · progress`), or keep only
   `flow` + `flow-router` and let the router dispatch agents directly?
2. **`tools/task_control`** — shrink to a minimal state file, or delete outright and let
   `flow-progress` read GSD's `.planning/STATE.md`? Does the harness need *any* task state of its own?
3. **Upstream skill dependency.** Methodology living in `npx skills@latest add mattpocock/skills`
   means an external, versionless dependency. Pin it, vendor it (license boundary!), or accept it?
4. **Phase 30's landed contract.** Keep `deny-domains.json` as a reference document (and fix it to
   declare `HARNESS_DEV_LIGHT`), or delete it and remove the declaration entirely? Under §0, is
   keeping an inventory nobody enforces worth the maintenance?
5. **Phase 33** — is any of SEAL-04 (`secret_scan` reads patterns from the contract) worth keeping,
   or does the move-to-CI change make it moot? SEAL-05 (portable ratification record) is proposed for
   deletion under §0; confirm or contest.
6. **RAT-4 / RAT-5 / deny-spelling** — proposed disposition: close all three with one recorded
   decision, "solo owner, merge is the ratification; the reviewer≠author model does not apply here,"
   rather than building a mechanism. Confirm or contest.
7. **ADR-0011** — accept as-is (with a note that its code preceded ratification), or supersede with a
   broader ADR-0012 covering the whole de-ceremony decision?
8. **Milestone shape.** One large v2.5, or split — v2.5 "de-ceremony + lifecycle swap" (fast,
   mostly deletion) and v2.6 "monorepo core B·C·D·E + harness-author A + install path F"? Sequencing
   matters: deleting first makes the additions cheaper to land, but leaves a window where lifecycle
   guidance is thin.
9. **Ordering risk.** Which additions must precede which deletions to avoid a broken intermediate
   state (emit-drift, `registry.lock`, `docs-guard`, the fan-in `gate` all reference names that are
   about to disappear)?
10. **Anything in §4.3 mis-bucketed** — specifically: is `golden` really goal-serving for a generic
    monorepo, or is it a log-parser trait that belongs in the instance alongside `polyglot_lint`?

Both reviewers must answer with §0 as a hard filter and flag any proposal of the author's that
violates it.
