# v2.3 Milestone Design of Record — Contract Graph, Brownfield Adoption, Living Docs

## 1. Milestone name + thesis

**v2.3 — Contract Graph, Brownfield Adoption, Living Docs.** v2.3 generalizes the shipped linear pipeline slot into a deterministic, authority-centered contract-relationship graph, then uses that graph as the vocabulary for safely adopting the harness into existing repositories and for detecting drift in human-authored documentation. The milestone adds only the missing data shapes, deterministic analyzers, and thin user-facing workflows: it preserves the linear pipeline unchanged as a lowered special case, stages adoption inside the existing task control plane, keeps constitution artifacts human-ratified, and extends the existing orchestrator and emitter surfaces without creating a second framework, contract engine, documentation oracle, or authority plane.

## 2. Requirements

Markers are final: **REUSE** composes shipped machinery unchanged; **NEW** introduces missing machinery; **NEW+REUSE** adds a narrow mechanism around named shipped primitives. Every requirement has exactly one owning phase in section 3.

### Theme A — General contract-relationship topology

- **TOPO-01 — Ratified canonical relationship contract.** `[Theme A] [NEW+REUSE]` A human-ratified Draft 2020-12 schema under `contracts/harness/topology/` shall define each relationship as a stable ID, tracked contract reference, exactly one explicit authority endpoint, one-or-more dependent endpoints, and optional explanatory kind/labels; positive and negative fixtures shall pass the existing contract hash/drift ratification path.
- **TOPO-02 — Additive pure-DATA slots and thin loaders.** `[Theme A] [NEW+REUSE]` Project and workspace TOML shall accept additive `[[contract_graph.relationships]]` records while all existing loader APIs and legacy configuration remain unchanged, and new accessors shall return raw data without validation, traversal, discovery, or domain policy.
- **TOPO-03 — Backward-compatible pipeline lowering.** `[Theme A] [NEW+REUSE]` One deterministic `effective_relationships()` path shall lower every legacy `[pipeline].edges` entry to an authority/dependent relationship and union it with explicit records, failing on duplicate IDs, duplicate semantic edges, or contradictions while leaving current linear fixtures byte-unchanged.
- **TOPO-04 — Canonical compiler and consistency gate.** `[Theme A] [NEW+REUSE]` A domain-neutral compiler and `harness_lint` gate shall emit stably ordered, repo-confined graph data and stable diagnostic codes, validate endpoints and authority-owned contract resolution, and accept fan-in, fan-out, disconnected components, and canonical cycles.
- **TOPO-05 — Bounded affected-set queries.** `[Theme A] [NEW+REUSE]` Direct, reverse, and transitive relationship-impact queries shall terminate on cycles and return deterministically ordered IDs and paths only, for conductor routing and documentation reports, without selecting new task evidence requirements or preloading contract bodies.
- **TOPO-06 — One generalized conductor surface.** `[Theme A] [NEW+REUSE]` The existing orchestrator, `/pipeline`, and `pipeline-map` skill shall consume the canonical graph, preserve the locked linear rendering, render branches/cycles safely, and round-trip from `harness/` to both runtimes byte-identically with no new graph command or persona.
- **TOPO-07 — Domain-neutral graph proof and decision record.** `[Theme A] [NEW+REUSE]` Generic project/workspace fixtures shall prove shared-contract fan-out, request and response as separate records, event fan-out, a legal cycle, and cross-repo authority resolution while the log-parser instance remains unchanged, GEN-04 twins stay green, and a human-ratified ADR records the model.

### Theme B — Brownfield adoption

- **ADOPT-01 — Bounded deterministic inventory.** `[Theme B] [NEW+REUSE]` A read-only local-root inventory shall deterministically report languages, package/component boundaries, existing schemas/specs/docs/ADRs/AGENTS/CODEOWNERS/CI surfaces, and candidate process boundaries using confined, ignored, size-capped evidence pointers and hashes while excluding secrets, binaries, vendors, generated output, and source dumps.
- **ADOPT-02 — Evidence-separated mapping plan.** `[Theme B] [NEW+REUSE]` Every proposed member, component, relationship, contract candidate, test command, documentation destination, and AGENTS boundary shall be classified as observed, inferred, or unknown with source evidence, and unresolved ownership shall remain a question rather than becoming invented authority.
- **ADOPT-03 — Complete destination/disposition manifest.** `[Theme B] [NEW+REUSE]` The adoption plan shall assign exactly one `create`, `marker-merge`, `preserve`, `conflict`, `derived-regenerate`, or `human-ratification-required` disposition to contracts, goldens, ADRs, all Diátaxis quadrants, both memory planes, task/config/workspace topology, root/nested AGENTS, CODEOWNERS guidance, runtime-neutral sources, and emitted runtimes.
- **ADOPT-04 — Task-local adoption batch.** `[Theme B] [NEW+REUSE]` Each adoption batch shall live under `.workflow/tasks/<task-id>/artifacts/adoption/<batch-id>/` and bind its inventory, plan, draft tree, questions, conflicts, source ref, task revision, artifact hashes, and approvals to the existing CAS, evidence, HANDOFF, and resume lifecycle.
- **ADOPT-05 — Structural constitution refusal and safe apply.** `[Theme B] [NEW+REUSE]` Discovery/draft modes shall write only inside the task artifact root, and apply mode shall atomically create or marker-merge reviewed non-constitution files, refuse silent overwrite and concurrent target drift, and reject `contracts/`, `docs/adr/`, and `golden/` destinations before mutation.
- **ADOPT-06 — Exact human ratification checkpoint.** `[Theme B] [NEW+REUSE]` Promotion shall require a human decision covering proposed contracts, goldens, ADRs, relationship authorities, conflicts, and unknowns, bound to exact draft hashes, task revision, and git ref so any changed input invalidates approval.
- **ADOPT-07 — One adoption workflow and three-fixture proof.** `[Theme B] [NEW+REUSE]` One thin `/adopt` command and `brownfield-adoption` skill shall compose the deterministic tool, existing explorer/fan-out/orchestrator/task gates, promotion workflows, and runbook, and three generic fixtures—polyglot single-repo, two-repo client/server, and partial-adoption/collision—shall prove idempotence, no arbitrary command execution, constitution refusal, emitter closure, and GEN-04; at least one fixture shall include CRLF and BOM input.

### Theme C — Human-authored documentation upkeep

- **DOCSUP-01 — Central dependency registry.** `[Theme C] [NEW+REUSE]` A reviewed `docs/doc-dependencies.toml` shall bind stable source selectors to human-authored target documents, disposition policy, and `required` or `advisory` severity while rejecting path escape, duplicate IDs, empty required selectors, derived/reference targets, and edit policies for accepted ADRs.
- **DOCSUP-02 — Exact fingerprints and review ledger.** `[Theme C] [NEW+REUSE]` A deterministic guard shall hash sorted source and target path/byte sets, and a committed ledger shall store only binding ID, exact reviewed digests, and `updated` or `reviewed-no-change` disposition—never time, person, prose copies, or model identity.
- **DOCSUP-03 — Classified, non-gameable staleness gate.** `[Theme C] [NEW+REUSE]` The guard shall classify bindings as `FRESH`, `BROKEN`, `STALE_REQUIRED`, `STALE_ADVISORY`, or `UNCOVERED`; fail `BROKEN` and `STALE_REQUIRED`, warn `STALE_ADVISORY`, enforce uncovered-count non-regression, and reject ledger-only digest bumps lacking a matching exact disposition.
- **DOCSUP-04 — Derived queue and bounded SessionStart pointer.** `[Theme C] [NEW+REUSE]` Existing memory-regeneration machinery shall deterministically render a pointer-only `.memory/derived/docs-staleness.md` queue and add at most one conditional SessionStart pointer line while preserving derived-never-hand-edited rules, byte-identical `assemble()`, and the existing approximately 4,000-character budget.
- **DOCSUP-05 — Constitution-safe report and disposition rules.** `[Theme C] [NEW+REUSE]` Stable reports shall group changed paths/hashes, graph impact IDs, target docs, severity, and required disposition; accepted ADRs shall yield only `REVIEWED_STILL_CURRENT` or `SUPERSEDING_ADR_REQUIRED`, contract/golden failures shall remain prior and authoritative, and old-to-new diffs shall be shown only when retrievable from git.
- **DOCSUP-06 — One bounded docs-update workflow.** `[Theme C] [NEW+REUSE]` One thin `/docs-update` command and `docs-upkeep` skill shall read the deterministic queue, draft bounded human-doc edits or exact review dispositions, and route through existing review/verify flows while structurally excluding accepted ADRs, `docs/reference/**`, `.memory/derived/**`, contracts, and goldens and round-tripping both runtimes.
- **DOCSUP-07 — Reviewed seeding and adoption integration.** `[Theme C] [NEW+REUSE]` A normal human-reviewed change shall seed bindings for the highest-risk existing docs and the adoption runbook, while `/adopt` may propose registry/ledger entries but shall leave inferred ownership unresolved and unable to become green without explicit review.

## 3. Phase breakdown

The implementation DAG is:

```text
24 ──> 25 ──> 28 ──> 29
 │                    ▲
 └──> 26 ──> 27 ──────┘
```

Theme A's ratified vocabulary is the shared foundation. The graph implementation/surfaces and the deterministic adoption spine then proceed independently. Documentation detection depends on completed graph queries, while the final docs workflow depends on both its guard and the adoption workflow it integrates.

### Phase 24 — Contract-Relationship Vocabulary and Compatibility

**Goal:** Ship the ratified graph record and additive configuration seam without forcing a migration.

**Owns 1:1:** `TOPO-01`, `TOPO-02`, `TOPO-03`.

**Dependency edges:** none.

**Sequencing rationale:** Contract-first requires the authority/dependents wire shape and legacy coexistence semantics to be fixed before either the graph compiler or brownfield mapper emits them. The phase is independently shippable because old configs remain valid and new configs gain an additive, validated vocabulary.

**Exit:** schema fixtures and human ratification complete; legacy lowering is byte-deterministic; current linear project/workspace/log-parser files require no edits; contract drift and GEN-04 are green.

### Phase 25 — Graph Compiler, Queries, Conductor, and Proof

**Goal:** Make the general relationship graph usable through one deterministic implementation and the existing user-facing topology surface.

**Owns 1:1:** `TOPO-04`, `TOPO-05`, `TOPO-06`, `TOPO-07`.

**Dependency edge:** `24 -> 25`.

**Sequencing rationale:** Compiler/gate/query behavior implements the ratified Phase-24 contract; conductor text and emitted runtimes must consume that single implementation rather than create a parallel interpreter.

**Exit:** stable compiler diagnostics and cycle-safe queries; authority-member resolution reuses existing drift checks; generic non-linear fixtures and unchanged linear regression pass; ADR is human-ratified; `/pipeline`, `pipeline-map`, and orchestrator re-emit byte-identically with no model ID; no task-control evidence-selection semantics change.

### Phase 26 — Deterministic Brownfield Inventory and Mapping

**Goal:** Produce a complete, evidence-grounded adoption plan without mutating the target or invoking an agent workflow.

**Owns 1:1:** `ADOPT-01`, `ADOPT-02`, `ADOPT-03`.

**Dependency edge:** `24 -> 26`.

**Sequencing rationale:** The mapper needs the Phase-24 record vocabulary but not the Phase-25 compiler, conductor, or queries. Keeping the pure tool phase independent and agent-free makes it fully CI-testable and lets Theme B proceed in parallel with Theme A's surfaces.

**Exit:** repeated inventory/plan output is byte-identical; every proposal is observed, inferred, or unknown; every harness destination has one disposition; confinement, secret exclusions, caps, ambiguity, and collision detection pass; target tree is unchanged.

### Phase 27 — Task-Local Adoption Workflow and Safe Application

**Goal:** Turn the deterministic plan into a resumable, human-ratified, non-destructive adoption workflow using the shipped task control plane.

**Owns 1:1:** `ADOPT-04`, `ADOPT-05`, `ADOPT-06`, `ADOPT-07`.

**Dependency edge:** `26 -> 27`.

**Sequencing rationale:** User-facing discovery and application must compose the verified inventory/manifest rather than rediscover the repository, and task CAS/evidence/HANDOFF must own the lifecycle before any reviewed write is attempted.

**Exit:** task-local batches resume safely; changed drafts/refs/revisions invalidate approval; constitution paths are rejected before mutation; non-constitution apply is atomic, collision-safe, and idempotent; three fixtures including normalization-dirty input pass; `/adopt` and its skill re-emit byte-identically with no new persona.

### Phase 28 — Human-Docs Registry, Guard, and Derived Queue

**Goal:** Detect and surface exact human-document review obligations without claiming semantic correctness or competing with derived generators.

**Owns 1:1:** `DOCSUP-01`, `DOCSUP-02`, `DOCSUP-03`, `DOCSUP-04`, `DOCSUP-05`.

**Dependency edge:** `25 -> 28`.

**Sequencing rationale:** Detection precedes the drive loop, and graph-aware reports require the final affected-set query. Adoption is not a hard dependency: it may later seed the registry, but its schedule must not hold the docs guard hostage.

**Exit:** registry validation, stable fingerprints, exact ledger checks, required/advisory classifications, coverage non-regression, ADR-safe dispositions, derived-queue determinism, injector byte identity, and budget tests pass; existing `/docs-sync`, `/refresh-memory`, and stale-derived semantics are unchanged.

### Phase 29 — Docs Drive Loop, Adoption Integration, and Milestone Closeout

**Goal:** Add the bounded human-facing docs workflow, connect adoption seeding, and close all three themes against the full existing gate fan-in.

**Owns 1:1:** `DOCSUP-06`, `DOCSUP-07`.

**Dependency edges:** `28 -> 29`; `27 -> 29`.

**Sequencing rationale:** `/docs-update` is composition over the deterministic Phase-28 guard, while adoption seeding can only be verified after Phase 27's destination manifest and command exist. This is the sole integration/closeout phase, not a new lifecycle engine.

**Exit:** `/docs-update` and `docs-upkeep` emit byte-identically to both runtimes; adoption proposes but cannot self-review bindings; required seeded docs are fresh or exactly dispositioned; accepted ADR/reference/derived exclusions are gate-tested; full pytest, contract drift, golden, workspace drift, stale-derived, lifecycle, GEN-04 twins, docs guard, emitter drift, no-model-ID lint, injector budget, and `git diff --check` are green.

## 4. Scope boundaries

The following are explicitly **OUT**:

- **No contract compatibility/versioning engine.** Distinct versioned schemas may be separate tracked contract paths, but semver ranges, migration graphs, backward/forward/full compatibility matrices, Pact, Buf, brokers, and schema registries would duplicate or outrun the existing hash/drift/golden safety net.
- **No impact-driven task evidence policy.** v2.3 supplies deterministic affected-set hints and reuses existing per-member gates; changing which evidence a v2.2 lane requires needs a later, separately ratified control-plane decision.
- **No topology runtime.** The graph is pure data plus static analysis, not service discovery, a message bus, network crawler, remote clone manager, daemon, scheduler, or distributed transaction layer.
- **No second orchestrator, router, graph command, or specialist persona.** `/pipeline`, `pipeline-map`, the existing orchestrator, explorer, and fan-out substrate evolve or are reused; GSD remains development-side and the risk router remains a pure function.
- **No new adoption authority or staging plane.** There is no `.workflow/adoption/`; adoption is an ordinary task with artifacts under `.workflow/tasks/<task-id>/`.
- **No autonomous contract extraction or brownfield migration.** `/adopt` drafts candidates and format scaffolding; it does not declare authority, infer goldens from behavior, refactor source, move repositories, rewrite CI/package managers, execute discovered scripts, or support remote workspace members.
- **No constitution self-ratification.** Agents cannot promote contracts, accepted ADRs, or goldens; CODEOWNERS, contract/golden gates, and explicit human checkpoints remain authoritative.
- **No derived-plane reimplementation.** `/docs-sync`, curator, `/refresh-memory`, and stale-derived retain exclusive ownership of reference/derived regeneration; the new queue is generated through existing memory machinery and never hand-edited.
- **No semantic documentation oracle or auto-commit.** Hashes prove declared review debt, not prose correctness; no model runs in CI, no LLM-only freshness score gates merges, and drafted prose still receives normal human review.
- **No accepted-ADR edits.** Documentation drift can produce `REVIEWED_STILL_CURRENT` or a superseding ADR draft only; accepted decisions are append-only.
- **No broad fixture or framework stack.** Exactly three adoption fixture shapes and focused topology/docs fixtures are sufficient; the integrated exit is gate composition, not a new mega-fixture or workflow framework.
- **No deferred v2.2 extensions.** TCP-F01 through TCP-F05, signed external evidence, and STRICT rollback remain deferred because they do not deliver Themes A/B/C and would reopen settled task-control surfaces.

## 6. Constraint-honoring checklist

- [x] **GEN-04:** all core schemas/tools/surfaces and fixtures are domain-neutral, core imports no instance, log-parser remains unchanged, and both independence guards are mandatory gates.
- [x] **Contract-first:** the relationship record is ratified before implementation, each relation resolves a tracked authority-owned contract, and docs/adoption follow rather than redefine contract truth.
- [x] **Machines gate / humans ratify:** machines inventory, lint, hash, draft, and refuse; humans approve constitution promotion, relationship authority, accepted/superseding ADRs, goldens, and exact review dispositions.
- [x] **No model ID:** configs, schemas, task artifacts, evidence, ledgers, HANDOFF, emitted files, fixtures, commits, PRs, and comments remain capability-neutral and pass the existing lint.
- [x] **Emitter round-trip:** every touched/new agent, command, and skill starts under runtime-neutral `harness/`, emits to `.opencode/` and `.claude/`, passes caps/manifests/snapshots, and is byte-identical on rerun; emitted files are never hand-edited.
- [x] **One orchestrator:** the existing orchestrator is extended in place; the risk router stays pure, GSD stays dev-side, and `/adopt` plus `/docs-update` compose existing explorer/fan-out/review flows.
- [x] **Reuse, not reimplement:** contract hash/drift, golden comparator, §4.3–4.6 normalization, config/workspace loaders, task CAS/evidence/HANDOFF, `/verify-work`, `/adr`, `/docs-sync`, `/refresh-memory`, and the emitter retain their authority and implementations.
- [x] **Determinism:** graphs, inventories, manifests, ledgers, reports, queues, and emitted outputs use stable ordering/serialization, content hashes, cycle-safe visited sets, no wall-clock hot-path values, bounded pointers instead of bodies, and the existing injector budget.

## 7. Open questions for the human

1. **Explicit TOML slot spelling:** approve `[[contract_graph.relationships]]` as the final public name? **Default: yes**—it is unambiguous and avoids the overly generic root-level `[[relations]]`.
2. **Initial required docs bindings:** which existing docs should block on staleness at launch? **Default:** root READMEs, root/nearest-wins AGENTS guidance, the task-lifecycle how-to, template-and-instances explanation, and the new adoption runbook; seed other bindings as advisory.
3. **Topology ADR number:** should planning reserve ADR-0009 for the relationship model if no intervening ADR lands? **Default: yes**, but allocate the next free number at implementation time rather than hard-coding a stale number.
