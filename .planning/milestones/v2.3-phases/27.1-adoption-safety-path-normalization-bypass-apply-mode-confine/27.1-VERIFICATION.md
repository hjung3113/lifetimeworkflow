## Judgement Call: are SC-1..SC-5 satisfied despite WR-05/WR-06/WR-07?

**Verdict: Yes, SC-1 through SC-5 are satisfied as literally written.** Reasoning:

- **SC-1** enumerates a specific hostile set: `contracts/x.json`, `./contracts/x.json`, `a/../contracts/x.json`, `CONTRACTS/x.json`, a symlink into `contracts/`, plus a legitimate negative control. It does not mention a bare `.` destination. I independently re-ran exactly this set live and every hostile case is refused, the legitimate case is allowed. WR-05's `.` case is a **different** input than anything SC-1 enumerates — it's a fresh, narrower defect discovered by the reviewer's own adversarial expansion beyond the roadmap's named set, not a failure of the named set.
- **SC-2** requires a spy on real write primitives proving zero writes for absolute/`..`-traversal destinations. Verified independently: the spy patches the actual `os.open`/`os.link`/`os.replace` calls the post-fix code uses, and the structural pre-check (executed before `.resolve()`) rejects both cases before any of those calls. WR-05's `.` crash happens in a completely different code path (`_existing_hash` opening a directory) that SC-2 never claimed to cover.
- **SC-3** requires `check_valid` be consulted and unpromoted/stale batches be refused, with specific reference to `(draft_hash, task_revision, git_ref)` staleness. That behavior is verified and works correctly for well-formed `approval.json` files (the only shape SC-3 discusses). WR-06 is about a **corrupted/malformed** `approval.json` — an input shape SC-3's text never mentions — crashing instead of returning `False`. Both defects fail *closed* (no filesystem write happens either way) — they are robustness/exception-hygiene gaps in already-existing controls, not unmet confinement or gating requirements.
- **SC-5** requires the seven named findings each carry a disposition. All seven do, and I independently confirmed each disposition's underlying claim is real (not merely test-shaped) by re-deriving CR-01/CR-02/CR-03 from source and by reading WR-01/WR-02/WR-03/WR-04's actual code changes rather than trusting the SUMMARY's prose. WR-02's disposition specifically claims "returns False on missing draft artifact" — a narrower claim than "check_valid never raises on anything" — and that narrower claim is true and test-proven. The disposition table does not overclaim; it does not say WR-02 makes `check_valid` universally exception-safe.
- **SC-4** is a pure contract/atomicity/drift criterion, unrelated to WR-05/WR-06 — fully verified independently.

WR-05, WR-06, and WR-07 are genuine new defects in the very controls this phase built, and they should not be silently dropped — they are carried forward here as explicit findings requiring their own disposition in a future phase (most naturally, a follow-up 27.1.1 or as part of whatever phase next touches `tools/adoption_apply`). But grading SC-1..SC-5 as unmet because the reviewer found *additional*, narrower-scope defects beyond what those criteria literally asked for would punish exactly the kind of honest, deeper adversarial discovery this phase exists to reward — the same "1096 green tests, still broken" pattern the phase's own charter was written to correct, this time applied one level too aggressively against fresh findings that are themselves evidence the review process is working. All three new findings fail closed (no bypass, no unconfined write, no unapproved apply) — none is a security-property regression of SC-1..SC-5's actual guarantees.

**Recommendation:** Track WR-05/WR-06/WR-07 as a small, cheap follow-up (all three fixes are 1-5 line changes per the review's own suggested patches) before or alongside Phase 28, since they touch the same `apply.py`/`approval.py` surface Phase 28+ will build atop. Do not block Phase 27.1's own closure on them.
