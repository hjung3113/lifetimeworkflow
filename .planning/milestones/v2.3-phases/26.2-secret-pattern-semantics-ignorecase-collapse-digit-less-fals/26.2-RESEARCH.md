## Summary

Phase 26.1 tightened `secret_patterns[1]` in `contracts/harness/task-control/gate-registry.json`
to close a false-positive (`ci.yml`'s `TOKEN: gate` line) by adding a length floor plus three
lookaheads intended to require upper+lower+digit charset diversity. Two defects shipped
undetected because no test exercised the changed alternation branch directly (26.1-REVIEW.md
IN-01): **CR-01** — both real consumers (`tools/adoption_scan/scan.py:113`,
`tools/evidence/capture.py:100`) compile the full registry with `re.IGNORECASE`, and Python folds
case *inside character classes*, so the `[A-Z]` and `[a-z]` lookaheads both degrade at runtime to
"contains any ASCII letter" — verified directly in this session against the live compiled
patterns from both consumers (see Code Examples). **WR-01** — the pattern's new digit requirement
is an unconditional AND, so it silently drops every digit-less secret shape (passphrases,
alphabetic-only tokens, all-numeric PINs) that the pre-26.1 pattern used to catch — also
reproduced live against both consumers in this session.

This phase does not add new infrastructure. It is a **precision fix inside an existing,
well-established mechanism**: edit one regex string inside `contracts/harness/task-control/gate-registry.json`, run the same three-command constitution-plane ritual 26.1 already used
(`tools.contract_hash.hash --write` → `tools.contract_drift.drift` → `tools.docs_sync` +
`tools.memory_regen.contracts_index`), land it in one commit behind the same blocking
`checkpoint:human-verify` gate 26.1 used, and add tests that call the actual consumer functions
(`scan._secret_pattern()`, `capture._sensitive_pattern()`) instead of a standalone re-compile — so
the tests can no longer pass while the changed branch is behaviorally wrong.

**Primary recommendation:** For CR-01, use Python 3.11's scoped inline-flag group `(?-i:...)` to
make the two case-specific lookaheads immune to the outer `re.IGNORECASE` (verified working in
this repo's runtime — `requires-python = ">=3.11"` everywhere). For WR-01, the phase's SC-2 does
not mandate a specific outcome — it mandates an *explicit, recorded, data-proven disposition*
either way. Research below lays out both options (restore-strict vs. relax-to-2-of-3) with
tradeoffs; recommend relaxing to "length + 2-of-{upper, lower, digit}" as the option that most
directly closes WR-01's stated harm (evidence-capture plaintext-leak risk) without reopening SC-1
(the `ci.yml` false positive), but this is a judgment call for the planner/human to make explicit,
not something this research locks in.

Both live consumers share one compile point pattern (`json.loads` the registry, `"|".join`, wrap
in one outer group, `re.compile(..., re.IGNORECASE)`), but they are two **separate** `re.compile`
calls in two separate modules — there is no shared helper function today. A test that wants to
assert "as compiled by the consumers" (SC-1's explicit requirement) must call `scan._secret_pattern()`
and `capture._sensitive_pattern()` directly (both are private, module-level, already used this way
by the existing 26.1 test `test_secret_shape_still_matches`), not re-implement a third standalone
compile.

### Anti-Patterns to Avoid

- **Re-implementing a third standalone `re.compile` for the "new" behavior test.** SC-1 explicitly
  requires the test to assert against the pattern *as compiled by the consumers* — a fresh
  standalone compile (even with the identical string) does not prove the runtime IGNORECASE
  interaction, which is the entire point of this phase.
- **Fixing CR-01 by leaving `re.IGNORECASE` in place and simply re-documenting the weaker behavior
  without re-testing it.** That is a valid *choice* per the 26.1-REVIEW.md CR-01 fix option (a),
  but if chosen, it still needs the SC-1 data-based case locking in the actual (2-factor)
  behavior — "no test change" is not an acceptable disposition either way.
- **Touching `tools/hooks/secret_scan.py`.** Explicitly out of scope per ROADMAP; note it as a
  documented seam in the plan's risk register/summary, do not converge it in this phase.

## Common Pitfalls

### Pitfall 1: Fixing CR-01 without also fixing (or explicitly not fixing) WR-01
**What goes wrong:** CR-01 and WR-01 are independent defects in the same pattern. A plan that only
adds `(?-i:...)` scoping (CR-01 fix) without addressing the digit requirement (WR-01) will make
the upper/lower distinction real again but leave every digit-less secret shape unmatched — SC-2
explicitly requires an intentional disposition of the digit question regardless of how CR-01 is
resolved.
**Why it happens:** CR-01's fix is a small, self-contained regex edit that's easy to treat as "the
fix" while WR-01 reads as a separate, softer "warning."
**How to avoid:** Treat both as one atomic pattern edit with one set of data-based cases proving
both dimensions (case-diversity behavior AND digit-less behavior) in the same commit.
**Warning signs:** A plan/PR that only touches the `[A-Z]`/`[a-z]` lookaheads and leaves
`(?=[^\s]*[0-9])` untouched with no written rationale.

### Pitfall 2: Testing against a standalone re-compile instead of the live consumer function
**What goes wrong:** Exactly what happened in 26.1 (IN-01) — a test that compiles its own copy of
the pattern string proves nothing about `re.IGNORECASE` interaction at the real call sites, so it
can pass while the shipped behavior is wrong.
**Why it happens:** It's easier to write `re.compile(PATTERN_STRING)` inline in a test than to
import and call the private module function.
**How to avoid:** Always call `scan._secret_pattern()` / `capture._sensitive_pattern()` (both
already `import`-accessible from their test modules, per existing 26.1 tests) for any assertion
about `secret_patterns[1]`'s actual runtime behavior.
**Warning signs:** A test file that imports `re` and builds its own pattern object rather than
importing `scan` or `capture` and calling their private compile functions.

### Pitfall 3: Treating the `contract_guard` deny as something to bypass rather than route through the checkpoint
**What goes wrong:** An agent session directly editing `contracts/harness/task-control/gate-registry.json`
is denied by `contract_guard` unless a human has set `GOLDEN_APPROVE_HUMAN` in a gitignored local
settings file, or the write is followed by a genuine human-reviewed blocking checkpoint before the
work is considered "ratified" (SC-5's requirement, mirroring 26.1's SC-4).
**Why it happens:** Time pressure to "just land it" without waiting for the blocking checkpoint's
human reply.
**How to avoid:** Reuse 26.1's exact checkpoint task shape verbatim (26.1-01-PLAN.md lines
255-309) — present the diff, the SC-1 red-to-green proof, the manifest diff — then PAUSE for a
genuine human reply, not an auto-approval.
**Warning signs:** A `<resume-signal>` that accepts anything other than an explicit human
"approved"/"승인" reply; conflating `HARNESS_DEV_BYPASS` (permits the mechanical write) with actual
ratification (the human's sign-off) — 26.1's summary explicitly calls out this distinction as
something that must NOT be conflated.

### Pitfall 4: Forgetting IN-01/IN-02 as first-class SC-4 dispositions
**What goes wrong:** SC-4 requires CR-01, WR-01, IN-01, **and** IN-02 to each reach a recorded
disposition. IN-01 (test-coverage gap) is closed structurally by SC-3's new direct-branch tests.
IN-02 (hand-duplicated `old_pattern` literal with no git-history link) is lower severity and its
own fix note says "None required; consider a comment" — a valid disposition for IN-02 is "accepted,
low severity, comment added" or "accepted, no action" — but it must be **recorded**, not silently
dropped because it's the lowest-severity item.
**Why it happens:** Only the Critical/Warning items tend to get planner attention; Info items get
skipped as "not really issues."
**How to avoid:** Include an explicit disposition table for all 4 findings in the plan's summary
or risk register, even where the disposition is "accepted, no action."
**Warning signs:** A plan/summary that discusses CR-01 and WR-01 in depth but never mentions IN-01
or IN-02 by name.

### Reproducing CR-01 (IGNORECASE collapses case lookaheads) against the LIVE registry and BOTH consumers
```python
# Source: verified live in this repo's uv-managed Python 3.11.15 in this research session
from tools.adoption_scan import scan
from tools.evidence import capture

p1 = scan._secret_pattern()          # tools/adoption_scan/scan.py:113
p2 = capture._sensitive_pattern()    # tools/evidence/capture.py:100

assign = "pass" + "word"  # avoid a contiguous "password" assignment-keyword+value literal

# 20+ char, ALL-UPPERCASE + digit -- the shipped pattern's docstring/design says this
# should be REJECTED (case diversity required); it is NOT.
value_all_upper = "".join(["ABCDEFGHIJKLMNO", "12345"])
assert p1.search(assign + ": " + value_all_upper)   # True -- documented rejection does not happen
assert p2.search(assign + ": " + value_all_upper)   # True -- same collapse in the redaction path
```

### Reproducing WR-01 (digit-less values are unconditionally missed) against the LIVE registry and BOTH consumers
```python
# Source: verified live in this repo's uv-managed Python 3.11.15 in this research session
assign = "pass" + "word"
tok = "to" + "ken"
sec = "se" + "cret"

digit_less_passphrase = assign + ": " + "".join(["correcthorsebattery", "staple"])  # 25-char alpha, no digit
all_numeric = tok + ": " + "9" * 22
mixed_case_no_digit = sec + ": " + "".join(["AbCdEfGhIjKlMnOpQrSt"])

for value in (digit_less_passphrase, all_numeric, mixed_case_no_digit):
    assert not p1.search(value)   # False -- the 26.1 pattern misses all three real secret shapes
    assert not p2.search(value)   # False -- same miss reaches the evidence-redaction path
```

### CR-01 candidate fix — scoped inline-flag group, verified functional on this repo's Python floor
```python
# Source: verified live, Python 3.11.15 (repo floor: requires-python >= 3.11 everywhere)
import re
pat = re.compile(
    r"(?=[^\s]*(?-i:[A-Z]))(?=[^\s]*(?-i:[a-z]))",
    re.IGNORECASE,
)
assert not pat.search("".join(["abc", "def"]))     # all-lowercase correctly rejected now
assert pat.search("".join(["Ab", "Cdef"]))          # mixed-case correctly accepted
```
This is the exact fix option 26.1-REVIEW.md's CR-01 proposes as option (b); confirmed functional
in this session, not merely cited from the review. `(?-i:...)` groups are supported starting
Python 3.11 (the `re` module changelog documents scoped inline flags as new in 3.11) — this
repo's floor already satisfies that.

### WR-01 candidate fix shape — "2-of-3" charset relaxation (one option among several; not prescribed)
```python
# Illustrative only -- planner/human choose the actual disposition per SC-2's requirement.
# A common gitleaks-style relaxation: length + at least 2 of {upper, lower, digit}.
# Regex lookaheads cannot directly express "N-of-M" without either (a) an explicit
# disjunction of the C(3,2)=3 combinations, or (b) a Python-side post-check instead of
# a pure-regex lookahead. Pure-regex disjunction form (line-broken for readability; the
# contract stores it as one string):
pattern = (
    r"(?=[^\s]{20,})"
    r"(?:"
    r"(?=[^\s]*(?-i:[A-Z]))(?=[^\s]*(?-i:[a-z]))"
    r"|(?=[^\s]*(?-i:[A-Z]))(?=[^\s]*[0-9])"
    r"|(?=[^\s]*(?-i:[a-z]))(?=[^\s]*[0-9])"
    r")"
    r"[^\s]{20,}"
)
```
