## Summary

This phase re-derives `secret_patterns[1]` behavior from scratch rather than trusting the plan/SUMMARY's claims, and independently confirms the core semantic claims hold:

- **`(?-i:...)` scoping is correct and complete.** Verified live against `re.IGNORECASE`: a
  single-case, digit-less 20-char value (`ABCDEFGHIJKLMNOPQRST`, `correcthorsebatterystaple`)
  does **not** match under either compiled form; a mixed-case digit-less value does. Reverting the
  scoping to an unscoped `[A-Z]`/`[a-z]` version reproduces the exact CR-01 collapse (confirmed by
  compiling the unscoped variant directly — it matches the all-upper digit-less fixture, proving
  `test_secret_patterns_1_case_diversity_survives_ignorecase` is a genuine regression guard, not
  an always-green tautology). The bare `[0-9]` classes are correctly left unwrapped — digits have
  no case, so wrapping them in a case-scoping group would be a no-op; not a latent bug.
- **Length floor is unchanged.** Dropping the old pattern's redundant leading length-lookahead
  does not weaken the floor — verified directly: a 19-char mixed-case value does not match, a
  20-char one does, both under the new pattern. This was already flagged as dead weight (WR-02)
  in 26.1-REVIEW.md and its removal here is correctly non-behavior-changing.
- **No new over-match window.** Each lookahead's scan is bounded by the same contiguous
  non-whitespace token the trailing consuming quantifier also consumes (a literal space terminates
  both) — it cannot examine or consume characters belonging to a different token. A diversity
  character appearing past position 20 within one long unbroken token does let that whole token
  match (verified), but this scanning behavior is unchanged from the pre-26.1 and 26.1 patterns
  (both used the same scan-ahead idiom) — not a regression introduced by this phase.
- **No ReDoS.** Re-timed independently (not just trusting the plan's claimed numbers): 200k-char
  no-match input in ~10ms, a 500k-char single-token no-match in ~26ms, 2000 repeated near-miss
  key/value tokens in ~6ms. No nested quantifiers, no catastrophic backtracking surface added by
  the three-branch disjunction.
- **Tests genuinely exercise the changed branch and would fail on regression.** Ran the new tests
  against the current registry (all green) and independently re-simulated both the pre-26.2 old
  pattern and a deliberately-unscoped variant against the new fixtures: the mixed-case-digit-less
  fixture fails against the old pattern (proving the WR-01 relaxation is a real, non-tautological
  change) and the all-upper-digit-less fixture matches against the deliberately-unscoped variant
  (proving the CR-01 regression guard is load-bearing, not decorative). Both consumers
  (`scan._secret_pattern()`, `capture_module._sensitive_pattern()`) are covered with mirrored
  fixtures.
- **No documented-vs-runtime mismatch remains.** Unlike the defect this phase closes, no prose
  documentation near the shipped code (docstrings in `scan.py`/`capture.py`, or the JSON contract
  itself, which cannot carry comments) makes a semantic claim about the pattern's diversity rule
  that could drift from the regex text — the executable test suite is now the only claim being
  made, and it is proven to match runtime behavior.
- **Process/governance facts hold up:** `tools.contract_drift.drift` exits 0 against the current
  tree; `contracts/.hashes/manifest.json` shows exactly one changed entry; the derived plane
  (`.memory/derived/contracts-index.md`, its snapshot twin) only changed the `gate-registry.json`
  row's `hash_prefix`, consistent with a machine regen, not a hand edit; commit messages carry no
  model identifiers; the IN-02 provenance comment correctly cites `d6e9054`, verified against
  actual git history.
- **Security direction (false-negative) re-check beyond the two accepted gaps:** worked through
  additional shapes an operator might call a "secret" — numeric-plus-punctuation PINs (still only
  satisfy the digit class, correctly excluded, same as the documented all-numeric gap),
  mixed-case-plus-symbols-no-digit values (correctly still match via the upper+lower branch). No
  additional undocumented false-negative shape was found beyond the two the phase explicitly
  accepted and recorded (single-case-only digit-less, all-numeric).

One genuine, if minor, gap was found in the test-authoring mechanics themselves (WR-01 below) —
the phase's own stated literal-avoidance convention and its own acceptance-criteria grep were not

## Warnings

### WR-01: New test fixtures use `"".join([single_literal])`, which does not actually break literal contiguity — violates the plan's own stated convention and acceptance criteria

**File:** `tools/adoption_scan/tests/test_scan_exclusions.py:158, 166, 197`; `tools/evidence/tests/test_capture.py:113, 121, 149`

**Issue:** The plan's `<behavior>` block states: "All fixture literals built via string
concatenation ... never a contiguous secret-shaped run in source," and Task 1's
`<acceptance_criteria>` explicitly requires: "No new test function's source contains a contiguous
secret-shaped literal (grep for ... a bare 20+-char alnum run, finds nothing outside `+`
concatenation)." Six of the newly added lines instead write forms like:

```python
value_all_upper = "".join(["ABCDEFGHIJKLMNOPQRST"])   # single list element — not concatenation
```

`"".join([...])` with a single-element list performs no splitting at all — the 20-char string
inside the brackets remains a single, unbroken literal token in the source file, identical in
effect to writing it bare. Running the exact grep the plan's own acceptance criteria specifies
confirms this — restricted to lines actually added in commit `cdc23f0`:

```
$ grep -noE '[A-Za-z0-9]{20,}' tools/adoption_scan/tests/test_scan_exclusions.py tools/evidence/tests/test_capture.py
tools/adoption_scan/tests/test_scan_exclusions.py:158:<20-char single-case run>
tools/adoption_scan/tests/test_scan_exclusions.py:166:<20-char mixed-case run>
tools/adoption_scan/tests/test_scan_exclusions.py:197:<20-char single-case run>
tools/evidence/tests/test_capture.py:113:<20-char single-case run>
tools/evidence/tests/test_capture.py:121:<20-char mixed-case run>
tools/evidence/tests/test_capture.py:149:<20-char single-case run>
```

(Pre-existing bare literals elsewhere in `test_capture.py` — e.g. the pre-26.2
`Sup3rSecretValue...`-shaped fixture used by an unrelated, unmodified test — are out of scope for
this phase and are not newly introduced here.)

This carries no live-secret or functional risk today: these six literals are single-case and
digit-less, so the consumer functions under test would not classify them as a secret value even
if scanned bare, and `tools/hooks/secret_scan.py` allowlists `tests/` paths outright. But it is a
real inconsistency between what the plan/SUMMARY claim was verified ("No new test function's
source contains a contiguous secret-shaped literal") and what actually shipped, and it sets a bad
precedent: a future fixture using this same `"".join([single_string])` idiom for an actually
digit-bearing, mixed-case 20+ char literal would produce a genuine contiguous secret-shaped run in
source while appearing, at a glance, to follow the repo's obfuscation convention.

**Fix:** Use real concatenation, matching the repo's own established idiom elsewhere in this same
diff (the `assign` / `sec` keyword fixtures already use two-piece `+` concatenation):

```python
value_all_upper = "ABCDEFGHIJKLMNO" + "PQRST"
```

or split the `join()` list into multiple elements so the call actually performs concatenation:

```python
value_all_upper = "".join(["ABCDEFGHIJK", "LMNOPQRST"])
```

## Info

### IN-01: Branch-attribution test proves index-1 involvement but not exclusivity

**File:** `tools/adoption_scan/tests/test_scan_exclusions.py` (`test_secret_patterns_1_branch_attribution`)

**Issue:** The test compiles `secret_patterns[1]` alone and confirms it matches the
mixed-case-digit-less fixture, then separately confirms the full alternation also matches the same
fixture. This is sufficient circumstantial evidence given the fixture's shape (the keyword-plus-
mixed-case-alnum fixture used here cannot structurally match any of the other seven
prefix/shape-anchored branches — AWS key prefix, GitHub token prefixes, `sk-`, `xox[bp]-`, PEM
header, JWT, `Authorization: Bearer`), so this is not a defect, but it is a weaker attribution
proof than its docstring implies ("pin that the match ... comes from registry index 1"): it does
not assert that the other seven branches do *not* also match this fixture, only that branch 1
alone is capable of matching it.

**Fix:** Optional strengthening, not required: additionally assert that compiling the alternation
of all `secret_patterns` entries *except* index 1 against the same fixture returns no match, to
make the exclusivity claim explicit rather than implicit in the fixture's shape.
