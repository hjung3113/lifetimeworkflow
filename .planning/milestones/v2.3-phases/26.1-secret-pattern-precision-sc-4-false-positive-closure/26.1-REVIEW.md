# Phase 26.1: Code Review Report

**Reviewed:** 2026-07-20T00:00:00Z
**Depth:** deep
**Files Reviewed:** 6
**Status:** issues_found

## Summary

The change tightens `secret_patterns[1]` in the constitution-plane contract
`contracts/harness/task-control/gate-registry.json` from an unbounded `key: value` matcher to a
length-gated, "3-way charset diversity" matcher (min 20 non-space chars, with an uppercase, a
lowercase, and a digit lookahead), intended to close SC-1 (the `.github/workflows/ci.yml` false
positive) while (per plan/research docs) still catching real secrets via a min-length + charset
heuristic.

The length-gate correctly closes SC-1: the false-positive line's value never contains a 20-char
contiguous non-space run, so that half of the fix is sound and verified empirically (no
catastrophic backtracking either — confirmed with adversarial 50k-char and 20k-repetition inputs,
sub-40ms).

However, **both real consumers compile this pattern with `re.IGNORECASE`**
(`tools/adoption_scan/scan.py:113`, `tools/evidence/capture.py:100`), and Python's `re.IGNORECASE`
folds case inside character classes. This silently collapses the intended uppercase/lowercase
lookaheads into two functionally-identical "contains any letter" checks — the pattern that ships
does **not** enforce 3-way (upper+lower+digit) diversity as documented in
`26.1-RESEARCH.md`/`26.1-01-PLAN.md` and asserted by the risk register (T-26.1-01). The actual
enforced rule is "≥20 non-space chars, containing at least one letter (either case) and one
digit." This is a real behavioral gap between the documented/reviewed security design and the
shipped artifact, and it is untested — no test in either commit exercises an all-lowercase or
all-uppercase 20+ char alnum value to confirm the documented rejection, so the gap ships silently
green. Separately (unaffected by the IGNORECASE issue), the tightened pattern introduces genuine,
concrete false-negative regressions vs. the old pattern for value shapes lacking a digit
character entirely (diceware-style passphrases, purely-alphabetic base64, all-numeric secrets) —
see WR-01 for detail.

Test quality is otherwise solid: the SC-1 red/green proof genuinely demonstrates the old pattern
matches the real `ci.yml` line and the live registry no longer excludes the file; the SC-2
seven-shape parametrized test proves each dedicated-shape branch (AKIA/ghp_/sk-/xox/PEM/JWT/Bearer)
is unaffected — none of those seven fixtures actually exercise `secret_patterns[1]` (the branch
that changed), so SC-2 proves the *other* branches didn't regress, not that the changed branch
behaves as documented (see IN-01). The `test_capture.py` fixture update is a like-for-like value
swap that preserves the original assertion's intent.

## Critical Issues

### CR-01: `re.IGNORECASE` neuters the documented upper/lower/digit charset-diversity requirement

**File:** `contracts/harness/task-control/gate-registry.json:12` (consumed at
`tools/adoption_scan/scan.py:113` and `tools/evidence/capture.py:100`)

**Issue:** Both consumers compile the full `secret_patterns` alternation — including
`secret_patterns[1]`'s new charset lookaheads — with the `re.IGNORECASE` flag (needed so the
keyword alternation `api[_-]?key|secret|password|token` matches `Password:`, `API_KEY=`, etc.).
Under `re.IGNORECASE`, Python folds case *inside character classes too*, so the two case-specific
lookaheads (one anchored on an uppercase-letter class, one on a lowercase-letter class) both
degrade to "contains at least one letter, of either case" — they no longer discriminate upper
from lower. Verified directly against the exact pattern text (values below written with the
repo's own literal-avoidance convention — concatenated, not contiguous — so this report itself
does not carry a live secret-shaped string):

```python
>>> import re
>>> assign = "pass" + "word"          # avoid a literal "password" assignment keyword+value run
>>> pat = re.compile(
...   assign + r"\s*[:=]\s*(?=[^\s]{20,})(?=[^\s]*[A-Z])(?=[^\s]*[a-z])(?=[^\s]*[0-9])[^\s]{20,}",
...   re.IGNORECASE)
>>> value_all_lower = "".join(["abcdefghijklmno", "12345"])   # all-lowercase + digits, 20+ chars
>>> bool(pat.search(assign + "=" + value_all_lower))
True   # documented design (26.1-RESEARCH.md Candidate B tradeoff note) says this should be MISSED
>>> value_all_upper = value_all_lower.upper()
>>> bool(pat.search(assign + "=" + value_all_upper))
True   # the same tradeoff note also documents this case as "would still be missed"
```

`26.1-RESEARCH.md` (Candidate B section) and `26.1-01-PLAN.md` explicitly document the design as
requiring "at least one uppercase letter, one lowercase letter, and one digit" and explicitly list
all-single-case+digit secrets as an accepted, documented tradeoff (i.e., the design assumed those
*would* be excluded, and the risk register relies on "3-way charset diversity" as the mitigation
for under-matching). The shipped pattern does not implement that design — it implements a
strictly weaker 2-factor check (letter-presence + digit-presence) under both real call sites. No
test in either commit (`2ef443d`, `d6e9054`) exercises this: the SC-2 fixtures don't touch
`secret_patterns[1]` at all (they hit dedicated named-shape branches — see IN-01), and the
RESEARCH.md's own "verified" reproduction snippet uses a value with **no digit at all**, so it
accidentally "passes" for an unrelated reason (missing digit) without ever exercising the
upper/lower distinction the snippet claims to prove. This means the documented security rationale
that was reviewed/approved for this contract change does not match the artifact that shipped, and
nothing in CI would catch a future regression here (e.g. if someone "simplifies" the pattern
further, believing the case-lookaheads are load-bearing when they are currently inert).

This is Critical because it is a security-relevant control whose actual enforced behavior
diverges from its own design documentation and passes its own test suite despite that divergence
— exactly the kind of gap adversarial review exists to catch, in a contract whose stated purpose
is an "auditable, gitleaks-style heuristic."

**Fix:** Either (a) accept and re-document the actual (weaker, 2-factor) behavior explicitly in
`gate-registry.json`'s comments/RESEARCH.md and add a regression test asserting an all-lowercase
20+ char + digit value MATCHES (documenting the real behavior), or (b) restore genuine 3-way
diversity by making the case-sensitive lookaheads immune to the outer `IGNORECASE` flag using
Python's scoped inline-flag group (requires Python ≥3.11):

```json
"(?:api[_-]?key|secret|password|token)\\s*[:=]\\s*(?=[^\\s]{20,})(?=[^\\s]*(?-i:[A-Z]))(?=[^\\s]*(?-i:[a-z]))(?=[^\\s]*[0-9])[^\\s]{20,}"
```
Then add a test that a same-case 20+ char + digit value does **not** match, to lock in whichever
behavior is chosen.

## Warnings

### WR-01: Digit-less secrets (diceware passphrases, all-numeric tokens, digit-free alphabetic runs) are new false negatives vs. the old pattern

**File:** `contracts/harness/task-control/gate-registry.json:12`

**Issue:** Independent of CR-01, the new pattern unconditionally requires a digit somewhere in
the run. The old pattern required nothing beyond non-whitespace. This is a real, likely-to-occur
regression class the old pattern caught and the new one misses entirely — confirmed with the old
vs. new compiled patterns:

- A long diceware-style passphrase assigned to `pass` + `word` (concatenated to avoid a live
  literal here), containing only lowercase letters and no digit: **old matches, new does not.**
- A purely numeric long value assigned to `to` + `ken` (all digits, no letters): **old matches,
  new does not.**
- A mixed-case, digit-free 28-character value assigned to `se` + `cret` (letters only, no digit):
  **old matches, new does not.**

These are realistic "real secret" shapes: long alphabetic API secrets, digit-less passphrases, and
numeric PINs/keys are common in the wild and are exactly the kind of secret this generic catch-all
branch exists to backstop, per its own stated purpose in `26.1-01-PLAN.md`'s risk register ("the
generic pattern's own residual catch-all still requires 20+ chars with 3-way charset diversity ...
so ad hoc `key: value` secrets without a dedicated shape are still caught unless they are short or
single-charset"). The risk register frames "single-charset" as the accepted, narrow exception, but
a long alphabetic-only passphrase is not "single-charset" in the colloquial sense operators would
expect this heuristic to catch — it reads as a clear, previously-undocumented regression for the
class of secret this catch-all is meant to be the backstop for. Because this pattern also feeds
`tools/evidence/capture.py::_sensitive_pattern()` (the evidence-capture redaction gate), a miss
here means such a secret is written **in plaintext** into a committed evidence artifact
(`artifacts/<gate>/<id>/output.log`), not merely under-flagged in an inventory scan.

**Fix:** Either loosen the digit requirement to "2-of-3 classes present" (a common gitleaks-style
relaxation — length + any two of {upper, lower, digit, symbol}) or explicitly document this as an
accepted residual gap in `26.1-RESEARCH.md`'s tradeoff table (it currently only documents the
all-lowercase-and-digit and all-uppercase cases as excluded — the digit-less case is not mentioned
as a tradeoff at all, suggesting it was not considered during design).

### WR-02: Redundant length assertion — lookahead length check duplicated by the consuming quantifier

**File:** `contracts/harness/task-control/gate-registry.json:12`

**Issue:** The pattern asserts a 20+-char lookahead, then — after three more lookaheads that
don't consume anything — consumes a `{20,}`-quantified run again. The leading lookahead is
functionally redundant: the trailing consuming quantifier already enforces the same length floor
on its own (a failed match on the trailing quantifier fails the alternation regardless). This is
harmless (confirmed no ReDoS: adversarially-sized inputs stay sub-40ms; no nested quantifiers) but
it is dead assertion weight that makes the pattern harder to audit — a reviewer has to notice it's
redundant rather than assume it does something the trailing quantifier doesn't already do.

**Fix:** Drop the leading length lookahead; the trailing quantified run already enforces the
length floor. (Low priority — purely a clarity/auditability nit, not a behavior change. Not
blocking.)

## Info

### IN-01: SC-2's seven fixtures don't exercise the changed branch (`secret_patterns[1]`)

**File:** `tools/adoption_scan/tests/test_scan_exclusions.py:130-144`

**Issue:** `test_secret_shape_still_matches`'s docstring says "SC-2: every one of the 7 unchanged
named secret shapes is still matched" — true, but potentially misleading in review: none of the 7
parametrized fixtures (AKIA…, ghp_…, sk-…, xoxb-…, PEM header, JWT, `Authorization: Bearer`) match
via `secret_patterns[1]` (the generic branch that was actually edited) — they each match their own
dedicated alternation branch (index 0, 2, 3, 4, 5, 6, 7). This test is a legitimate no-regression
proof for the *other seven* patterns, but it provides zero direct coverage of the one pattern this
phase changed. That gap is exactly why CR-01 and WR-01 went undetected by the test suite.

**Fix:** Add an explicit positive/negative pair against `secret_patterns[1]` specifically (a
mixed-case + digit 20+ char value matches; a same-case-only or digit-less value does not, per
CR-01/WR-01's chosen resolution).

### IN-02: `old_pattern` in the SC-1 red-check is a hand-duplicated literal, not sourced from history

**File:** `tools/adoption_scan/tests/test_scan_exclusions.py:116-118`

**Issue:** `test_ci_yml_false_positive_closed` hardcodes a second copy of the pre-fix regex string
to prove the "red" half of the red-green proof. This is fine as a one-time historical proof, but
it is a second source of truth for "what the buggy pattern was" that has no mechanical link to the
git history it's meant to document — if someone touches this literal later without understanding
its provenance, the red-check silently stops proving what its docstring claims. Low-severity;
acceptable as committed given the docstring is explicit about intent.

**Fix:** None required; consider a comment pointing at the specific pre-fix commit this literal
was copied from, for future auditability.
