# Plan 37-02 — LANE-04: Skill `registry.lock` + Adapter CI

**Requirement:** LANE-04 (TCP-F04) — the emitted skill surface must not be able to drift from its
declaration. Mirrors the existing `emit-drift` gate's posture.

**Goal (goal-backward):** editing a skill's description, adding a `references/` file, or emitting a
skill to only one runtime must FAIL a gate. Today all three pass `emit-drift` green (37-RESEARCH §4).
If I cannot show each of the three caught, the plan failed.

## Design in one paragraph

`harness/skills/registry.lock` is a committed, deterministic JSON declaration of the skill surface:
per skill, the SHA-256 of its description, the SHA-256 of every authored source file, the emitted
target paths in **both** runtimes (read from `tools/harness_emit/emit-manifest.json`, not recomputed),
and the discipline ids that name the skill. `tools/skill_registry` recomputes that structure and
either compares (`--check`, default) or rewrites (`--write`). A `registry-lock` CI job runs
`--check`, in the shape of the shipped `emit-drift` / `drift` / `stale-derived` jobs, and joins the
fan-in `needs` list.

## Tasks

### T1 — `tools/skill_registry/` package (pyproject in the SAME commit)

- `tools/skill_registry/pyproject.toml` — `harness-skill-registry`, stdlib only.
- `tools/skill_registry/registry.py`:
  - `LOCK_PATH = REPO_ROOT / "harness" / "skills" / "registry.lock"`.
  - `build_registry(...) -> dict` — for each `harness/skills/<name>/`:
    - `description_sha256`: SHA-256 of the UTF-8 `description` **string** parsed out of the
      SKILL.md frontmatter (reuse the frontmatter parser the harness_lint skill tests already use;
      do not hand-roll a second YAML reader).
    - `sources`: `{relative POSIX path: sha256 of raw bytes}` over every regular file in the skill
      directory, skipping symlinks (mirror `project_skill.iter_reference_files`'s traversal defence).
    - `emitted`: sorted paths from `tools.harness_emit.manifest.load_manifest(EMIT_MANIFEST)` whose
      normalized form starts with `.claude/skills/<name>/` or `.opencode/skill/<name>/`. **Reused,
      not recomputed** (D-10).
    - `disciplines`: sorted discipline ids from `harness/disciplines.toml` whose `skill` == name.
  - Top level: `{"tool": "tools.skill_registry", "version": 1, "skills": {...}}`.
  - `dumps(registry) -> str` — `json.dumps(..., sort_keys=True, indent=2) + "\n"` (the
    `manifest.prune_then_write` determinism contract).
  - `diff_lock(current, recomputed) -> list[str]` — human-readable, per-skill, naming
    added / removed / changed-description / changed-source / changed-emitted-set / changed-disciplines.
    A generic "files differ" message is not actionable and is not acceptable here.
- `tools/skill_registry/__main__.py`:
  - default / `--check`: exit **0** clean, exit **1** on drift printing `diff_lock` plus the exact
    fix command (`uv run python -m tools.skill_registry --write`), copying the `emit-drift` job's
    message discipline.
  - `--write`: rewrite the lock, print what moved.
- `tools/skill_registry/tests/conftest.py` — repo root on `sys.path`; verify
  `uv run pytest tools/skill_registry` **ALONE**.
- `tools/skill_registry/tests/test_skill_registry.py` — build against a tmp fixture tree, plus the
  three MUTATION proofs from the goal statement (description edit / new reference file / emitted
  path removed) each shown flipping `--check` red on a **copy**, never the real files.

### T2 — generate and commit `harness/skills/registry.lock`

- `uv run python -m tools.skill_registry --write`, then `--check` must exit 0 twice in a row
  (idempotence is the determinism proof).
- The lock lives under `harness/skills/` — the declaration plane it locks, not under `tools/`.
- Confirm it is NOT swept into the emitter's owned set: `registry.lock` is not a `SKILL.md` and not
  under `references/`, so `generate.emit` must ignore it. **Verify by re-emitting and checking
  porcelain**; if the emitter would copy it, move the lock to `harness/registry.lock` instead and
  say so in the SUMMARY.

### T3 — `registry-lock` CI job

- `.github/workflows/ci.yml`: a new job after `emit-drift`, same steps
  (`checkout` → `setup-uv` → `uv sync --all-packages` → `uv run python -m tools.skill_registry --check`),
  with a header comment stating **what this catches that `emit-drift` cannot** (§4 of the research).
- Add `registry-lock` to the fan-in job's `needs` list (`ci.yml:381`).
- Check whether a `harness_lint` test asserts the CI job set / fan-in list; if so it moves in the
  SAME commit.

### T4 — a live gate inside the suite

`tools/harness_lint/tests/test_skill_registry_lock.py`: the committed lock equals a fresh recompute.
This makes the lock a `uv run pytest` failure too, so it is caught before CI — the same
belt-and-braces the discipline wiring lint has. One mutation proof: a doctored copy of the lock
fails the comparison.

### T5 — verification

- `uv run pytest tools/skill_registry` (alone) · `uv run pytest -q` · ruff baseline · emit
  round-trip porcelain-empty · `python3 tools/harness_lint/workspace_check.py`.
- The **demonstration** for the SUMMARY: edit a skill description, run `--check`, show exit 1 and
  the named skill; revert.

## Risks

- **Ordering vs 37-01.** 37-01 edits skill bodies and `harness/disciplines.toml`, both of which the
  lock covers. Land 37-01 FIRST, then generate the lock, or the lock is born stale.
- **`emit-manifest.json` churn.** If 37-01 adds or removes an emitted skill path the lock must be
  regenerated in the same commit as the manifest. Both are `--write`-able; neither is hand-edited.
- **False determinism.** A lock that embeds an absolute path or an unsorted set will thrash. Keys
  are repo-relative POSIX and every collection is sorted; the two-run idempotence check in T2 is the
  proof, not the intent.
