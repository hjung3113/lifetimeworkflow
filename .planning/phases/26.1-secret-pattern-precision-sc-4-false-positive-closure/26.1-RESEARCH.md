## Summary

This phase edits exactly one array (`secret_patterns`) inside one already-tracked constitution-plane
JSON contract, `contracts/harness/task-control/gate-registry.json`. There is no new module, no new
test file location, no new consumer to wire up — the two existing consumers
(`tools/adoption_scan/scan.py::_secret_pattern()` and `tools/evidence/capture.py::_sensitive_pattern()`)
already read the array as **DATA** (`"(?:" + "|".join(patterns) + ")"`) and will pick up the tightened
4th pattern automatically. `tools/hooks/secret_scan.py` is a distinct, path-only secret-file gate — it
does **not** read `secret_patterns` and is unaffected.

The only pattern that needs to change is the 4th array element,
`(?:api[_-]?key|secret|password|token)\s*[:=]\s*[^\s]+` — the generic, prefix-less "key: value" catch-all.
The other 7 named-shape patterns (AWS key-id shape, GitHub PAT prefixes, `sk-…`, Slack `xox[bp]-…`, a
private-key PEM header, JWT, `Authorization: Bearer …`) are unaffected by design and must be proven
still-matching with one positive data-based test case each (SC-2) — none of them route through the
generic pattern.

**Primary recommendation:** Tighten only pattern index 1 (the generic `key/secret/password/token` value
matcher) to require a minimum-length, multi-charset value via bounded regex lookaheads — a pure JSON-data
edit, no Python code change required in either consumer. Pair the edit with: (1) a positive test file
per SC-2 named shape, (2) a negative test proving `.github/workflows/ci.yml`'s real false-positive line
no longer matches, (3) `tools.contract_hash.hash --write` rebaseline, (4) `tools.docs_sync` +
`tools.memory_regen.contracts_index` regeneration (both are no-ops in output content for this specific
file — see Pitfall 3 — but must still run per the committed procedure), and (5) the existing
`checkpoint:human-verify` blocking-task template from Phase 26 Plan 01, reused verbatim.

**IMPORTANT — live confirmation during this research session:** writing a literal PEM-header string
directly into a draft of this document was **refused by this repo's own PreToolUse `secret_scan` hook**
mid-session (exit refusal, no file written). This is direct, first-hand proof that at least one
content-based secret detector in this repo operates independently of `gate-registry.json`'s
`secret_patterns` array and inspects prose/documentation writes, not just source-code writes. The
planner must budget for the same constraint when the plan itself, its SUMMARY, or any test fixture
needs to reference a secret-shaped literal — always build such strings via concatenation, never as a
contiguous literal (see Pitfall 1, expanded below with this direct evidence).

## Where `_secret_pattern()` Lives and How It Is Consumed

`[VERIFIED: repo source, tools/adoption_scan/scan.py]`

```python
# tools/adoption_scan/scan.py:108-113
@functools.lru_cache(maxsize=1)
def _secret_pattern() -> re.Pattern[str]:
    """Compile the committed ``secret_patterns`` registry, read as DATA (never retyped)."""
    registry = json.loads(_GATE_REGISTRY_PATH.read_text(encoding="utf-8"))
    patterns = registry["secret_patterns"]
    return re.compile("(?:" + "|".join(patterns) + ")", re.IGNORECASE)
```

- `_GATE_REGISTRY_PATH = _REPO_ROOT / "contracts" / "harness" / "task-control" / "gate-registry.json"`.
- Cached once per process (`functools.lru_cache(maxsize=1)`) — no per-call re-read; tests that mutate
  the registry mid-process must account for this (none currently do; the existing test suite reads the
  real committed registry unmodified).
- Called from `classify_exclusions()` at step 8 (of a fixed path-first ordering: symlink-escape →
  vendored → generated → size cap → binary → generated-content-marker → secret-path glob →
  source-dump-banner marker → **secret-content pattern**), against `text_prefix` — the UTF-8-decoded
  first 64 KiB of the file (`_CONTENT_PREFIX_BYTES = 64 * 1024`), never the whole file:

```python
# tools/adoption_scan/scan.py:262-264
if _secret_pattern().search(text_prefix):
    return {"path": rel, "size": size, "excluded": "secret-content"}
```

- The exclusion record is `{"path": rel, "size": size, "excluded": "secret-content"}` — never the
  matched bytes, never a content hash for this branch (D-10 no-echo rule, enforced by
  `test_secret_content_excluded_and_not_echoed` in `tools/adoption_scan/tests/test_scan_exclusions.py`).

**Second consumer** `[VERIFIED: repo source, tools/evidence/capture.py]`:

```python
# tools/evidence/capture.py:94-100
def _sensitive_pattern() -> re.Pattern[str]:
    patterns = _registry().get("secret_patterns")
    if not isinstance(patterns, list) or not all(isinstance(item, str) for item in patterns):
        raise EvidenceError("invalid secret pattern registry")
    return re.compile("(?:" + "|".join(patterns) + ")" if patterns else r"(?!)", re.IGNORECASE)
```

## Regex Design Options for "Secret-Shaped Value"

All three candidates below use **bounded lookaheads** (`(?=...)`), which are linear-time in Python's
`re` engine for a fixed-length assertion against an already-anchored position — none introduce nested
unbounded quantifiers (`(a+)+` style) that could cause catastrophic backtracking. All are portable to
any regex engine supporting lookahead (JS `RegExp`, .NET `Regex`, PCRE) since this repo's data
contract is JSON-string patterns that could in principle be read by a non-Python consumer later
(`tools/evidence/capture.py` already does; a hypothetical `.NET` consumer would work identically —
lookahead syntax is Perl-compatible and standard across these engines).

`[ASSUMED: none of these three candidates have been run against the full committed registry test
suite in this session beyond the ad hoc Python verification below — the planner/executor must still
run `uv run pytest tools/adoption_scan/ tools/evidence/` after landing the final chosen pattern.]`

### Candidate A — min-length 16 + mixed alnum + restricted final charset
```
(?:api[_-]?key|secret|password|token)\s*[:=]\s*(?=[^\s]{16,})(?=[^\s]*[A-Za-z])(?=[^\s]*[0-9])[A-Za-z0-9+/=_.\-]{16,}
```
- Requires the captured run to be ≥16 non-space chars, contain at least one letter AND one digit, and
  restricts the FINAL consumed characters to a base64/token-like charset (`A-Za-z0-9+/=_.-`).
- Tradeoff: the restricted final charset can under-match real secrets containing other symbols (e.g.
  `&`, `!`, `#`) — a 17-char mixed-charset password value containing an `&` was REJECTED in this
  session's verification because `&` falls outside the allowed final charset, even though it clearly
  meets a length+mixed-charset bar. Verified empirically in this session (see below).

### Candidate B — min-length 20 + upper+lower+digit present, unrestricted final charset (RECOMMENDED)
```
(?:api[_-]?key|secret|password|token)\s*[:=]\s*(?=[^\s]{20,})(?=[^\s]*[A-Z])(?=[^\s]*[a-z])(?=[^\s]*[0-9])[^\s]{20,}
```
- Requires ≥20 non-space chars with at least one uppercase, one lowercase, and one digit present
  anywhere in that run (three-of-three charset diversity — a common secret-scanner entropy proxy,
  e.g. gitleaks' generic rules use a similar length+charset heuristic). Final consumed class is
  `[^\s]+` (unrestricted), so no legitimate symbol-containing secret is excluded by charset alone.
- Tradeoff: an all-lowercase-and-digit secret (common for hex tokens, though those already have
  dedicated patterns in this registry) or an all-uppercase env-var-style secret would still be missed
  by THIS generic fallback pattern — acceptable because none of SC-2's 7 named shapes route through
  it (each has its own dedicated pattern), and the generic pattern's purpose is a best-effort catch-all
  for ad hoc `key: value`-style secrets, not a guarantee.

### Candidate C — min-length 24 + 3-of-4 char classes via non-greedy scan
```
(?:api[_-]?key|secret|password|token)\s*[:=]\s*(?=[^\s]{24,})(?=.*?[A-Z])(?=.*?[a-z])(?=.*?[0-9])[^\s]{24,}
```
- Same idea as B with a higher length floor (24) and non-greedy lookahead scans (`.*?` instead of
  `[^\s]*`) — functionally near-identical to B for this use case since the surrounding context has
  already anchored to a non-space run; the `.*?` variant is slightly more expensive (can scan past a
  space if not careful) and offers no real precision benefit over B's `[^\s]*` form. Not recommended
  over B; included for completeness since it more closely resembles "3-of-4-classes" heuristics some
  external secret scanners (e.g. some gitleaks generic rules, truffleHog entropy checks) use as a
  reference point, but a true 4th class (symbol) requirement was deliberately excluded from all three
  candidates here — over-constraining to require a symbol would reject many real high-entropy
  alphanumeric-only API keys (e.g. Stripe-style keys, already handled by their own dedicated `sk-`
  pattern, but the generic pattern should not assume all symbol-free strings are safe).

| Input shape | A | B | C |
|---|---|---|---|
| short benign `TOKEN:`-style comment value (SC-1's real bug shape) | reject | reject | reject |
| `password: ${{ secrets.X }}` (GitHub Actions expression reference) | reject | reject | reject |
| `api_key: <redacted>` (placeholder) | reject | reject | reject |
| ordinary prose containing the word "secret" followed by a short non-secret value | reject | reject | reject |
| 28-char mixed-alnum value after `api_key=` | **match** | **match** | **match** |
| 17-char mixed value containing a symbol (`&`) after `password:` | reject (too short for B/C's 20/24 floor; A also rejects due to restricted final charset) | reject (17 < 20) | reject (17 < 24) |
| 28-char mixed-alnum value after `generic_token=` | **match** | **match** | **match** |

**Recommendation: Candidate B.** It closes SC-1 (all benign strings rejected), does not artificially
restrict the final charset the way A does (avoiding false negatives on real secrets containing `&`,
`!`, etc.), and its 20-char floor plus 3-way charset-diversity requirement is a reasonable, auditable
proxy for "secret-shaped" without requiring a code-level entropy calculation. It uses the exact same
`\s`/`[^\s]` escaping convention as the existing registry entries, so it round-trips through
`json.loads`/`json.dumps` cleanly (verified in this session):

```json
"(?:api[_-]?key|secret|password|token)\\s*[:=]\\s*(?=[^\\s]{20,})(?=[^\\s]*[A-Z])(?=[^\\s]*[a-z])(?=[^\\s]*[0-9])[^\\s]{20,}"
```

## Common Pitfalls

### Pitfall 1: Writing a contiguous secret-shaped literal into any new file (test, plan, or research doc) can be REFUSED by this repo's own write-time secret detector — proven first-hand this session
**What goes wrong:** A first attempt to write THIS research document, when it contained a literal
private-key PEM header string in a code example, was refused outright by the repo's PreToolUse
`secret_scan` hook mid-session (no file written, explicit refusal message naming the matched secret
shape). This is not a theoretical risk — it happened while producing this very research artifact.
`tools/adoption_scan/tests/conftest.py`'s own AWS-key fixture independently documents the same
constraint, building its literal via string concatenation ("so this fixture's own source text never
carries a contiguous secret-shaped literal — the repo's own `secret_scan` PreToolUse hook would
otherwise refuse to write this very file").
**Why it happens:** At least one content-based secret detector operates on write, independent of (and
possibly in addition to) `tools/hooks/secret_scan.py`'s path-only glob check and `gate-registry.json`'s
own `secret_patterns` array — its exact implementation was not pinned down in this session (see Open
Question 3).
**How to avoid:** Follow the `tmp_minirepo` precedent exactly for EVERY SC-2 positive test literal and
for any documentation/plan text that needs to reference a secret shape: build the string via
concatenation (e.g. two literal fragments joined with `+`, or an f-string built from a short prefix
constant plus a repeated-character suffix) so no single contiguous secret-shaped run appears in the
written source. Apply this to the PLAN.md itself, not just test code — plan/research documents are
written by the same tool and are subject to the same refusal.
**Warning signs:** A file write that inexplicably gets refused during test or plan authoring — check
for the concatenation workaround already used elsewhere in the repo (this file, `conftest.py`) before
assuming a bug in the write path.

### Pitfall 2: Drift gate is RED between editing the JSON and rebaselining
**What goes wrong:** Editing `gate-registry.json`'s content changes its RFC-8785 canonical hash
immediately; `tools.contract_drift.drift` will report it as drifted until `tools.contract_hash.hash
--write` is re-run. This is the same ordering hazard `26-01-PLAN.md`'s own `read_first` block flagged
for schema additions ("Pitfall 2: Drift gate is RED between authoring and rebaselining" — reused
directly from `26-RESEARCH.md`).
**Why it happens:** The manifest is a point-in-time hash snapshot; drift is computed by comparing live
vs. committed baseline.
**How to avoid:** Sequence strictly: edit JSON → `contract_hash --write` → `contract_drift.drift`
(expect 0) → derived-plane regen → commit everything together (SC-3's "one atomic commit").
**Warning signs:** `contract_drift.drift` exits non-zero immediately after the JSON edit — expected at
that intermediate point, not a bug, as long as the rebaseline step follows before the commit.

### Pitfall 3: `tools.docs_sync` produces an empty diff for this specific contract — do not mistake a no-op for a broken regen
**What goes wrong:** `tools/docs_sync/generate.py::iter_schemas()` globs `contracts/**/*.schema.json`
only (`[VERIFIED: tools/docs_sync/generate.py:214]`, `root.glob(f"**/*{_SCHEMA_SUFFIX}")` where
`_SCHEMA_SUFFIX` is `.schema.json`). `gate-registry.json` is a plain `.json` data contract, NOT a
`.schema.json` file, so `docs_sync` will NOT emit or change any `docs/reference/*.md` page for this
edit — its diff is legitimately empty for this specific file, even though SC-3 requires the command to
be RUN.
**Why it happens:** `docs_sync` and `contract_hash`/`contract_drift` use two different discovery globs
over `contracts/` — one schema-suffix-only, the other (`DATA_CONTRACT_PATHS` in `contract_hash`) an
explicit allowlist that DOES include `gate-registry.json`.
**How to avoid:** Run `tools.docs_sync` anyway (per the committed procedure / SC-3 wording), but do not
treat "no diff under `docs/reference/`" as a failure signal — it is the CORRECT, expected outcome for
this particular contract file. `.memory/derived/contracts-index.md`, by contrast, DOES change (its row
for `contracts/harness/task-control/gate-registry.json` carries a `hash` column sourced from
`build_manifest()`, which DOES include this file) — that file's diff must be committed.
**Warning signs:** A plan step that asserts "docs_sync produced a diff" will fail acceptance for this
specific phase; write the acceptance criteria to allow (or explicitly expect) an empty `docs/reference/`
diff while still requiring the command to have been run and to exit 0.

### Pitfall 4: `test_no_spurious_exclusions`'s existing assertion does not currently exercise the SC-1 bug
**What goes wrong:** As documented above (§Existing Test Coverage), the current `tmp_minirepo` fixture's
`ci.yml` content does not contain the false-positive-shaped string that triggers the real bug — so the
existing test suite is GREEN today regardless of whether the pattern is fixed, and would stay GREEN
even if a regression reintroduced the bug in a different form.
**Why it happens:** The synthetic fixture was authored (Phase 26) before this specific false positive
was discovered against the REAL repo's own `ci.yml`; the fixture was never updated to reproduce it.
**How to avoid:** The planner MUST add either (a) a comparably-shaped short comment line to
`tmp_minirepo`'s `ci.yml` fixture content that mirrors the real repo's false-positive shape (short,
benign value after the colon), or (b) a standalone test that runs
`scan._secret_pattern().search(Path(".github/workflows/ci.yml").read_text())` against the real
committed `.github/workflows/ci.yml` and asserts no match — SC-1's literal wording ("does not match
this repo's own `.github/workflows/ci.yml`") points toward (b) as the more literal proof, with (a) as a
useful synthetic-fixture companion.
**Warning signs:** A "SC-1 satisfied" claim backed only by the pre-existing (unmodified)
`test_no_spurious_exclusions` test is not actually proof — verify the new/modified test fails against
the OLD pattern and passes against the NEW one (red-green proof), not just passes against the new one.
