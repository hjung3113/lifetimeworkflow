<objective>
Implement `tools/adoption_apply/approval.py`: the ADOPT-06 human-ratification gate, modeled 1:1 on
`tools/golden_runner/approve.py`'s refuse-by-default pattern (an `--approve` flag, a reference, and
a human-matched confirmation value, all three independently required, first-missing-signal raises).
Where `/golden-approve` binds to `(case, adr_id)`, this gate binds to `(draft_hash, task_revision,
git_ref)` — recomputed FRESH at every validity check, never cached from an earlier call (RESEARCH
Pitfall 2: `handoff.py::validate()`'s strict exact-match ref check, not a "compatible"/"descendant"
fuzzy match, is the correctness bar).

Purpose: this is the machinery that makes ADOPT-06's "입력 변경 시 승인이 무효화된다" (approval is
invalidated by ANY input change) a proven property, not a prose claim — and, composed with Plan
27-01's `batch.py`, is where SC-1's full resume+invalidation cycle gets its end-to-end proof.
Output: `approval.py` + its full invalidation test suite, all green.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Human `--approve` + confirmation value → `promote()` | The only sanctioned human-ratification path; an agent must not fabricate the confirmation value. |
| Approval record → target-tree mutation (Plan 27-03's `apply.py`) | An approval is a NECESSARY but not itself SUFFICIENT precondition for apply — `apply_manifest` still performs its own drift/constitution checks independently; approval and apply are deliberately decoupled layers. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-27-04-01 | Spoofing | Approval replay across a rewound/rebased ref | mitigate | Exact-equality binding on `(draft_hash, task_revision, git_ref)`, recomputed fresh at every `check_valid` call — never a "compatible"/"descendant" match (Pitfall 2), proven by three independent single-axis invalidation tests. |
| T-27-04-02 | Elevation of Privilege | Agent self-approval (no human approve flag/confirmation) | mitigate | `promote()`'s three-signal refuse-by-default order, identical to `/golden-approve`'s proven pattern; `test_refused_without_human_confirmation`/`test_refused_without_approve_flag` are the automated proof. |
| T-27-04-03 | Repudiation | A cached/stale validity result being trusted instead of a fresh recompute | mitigate | `check_valid` never reads a cached value — every call recomputes the draft hash, task revision, and git ref fresh. |
| T-27-04-SC | Tampering (supply chain) | N/A | accept | Zero new package installs (`jsonschema` already a workspace dependency; stdlib `subprocess`/`hashlib`/`os` otherwise); no slopcheck required. |
