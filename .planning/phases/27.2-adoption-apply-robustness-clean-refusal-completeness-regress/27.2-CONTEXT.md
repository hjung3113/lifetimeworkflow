<decisions>
## Implementation Decisions

### Decided (Claude's discretion, autonomous mode)

| # | Grey area | Decision | Rationale |
|---|-----------|----------|-----------|
| D-01 | WR-05: refuse directory-shaped destinations in the guard, or handle the write error at the call site? | **Refuse in the `refuse_unsafe_destination` choke point** — a directory-shaped destination is an *unsafe destination*, decided before any filesystem touch. The `cli.py` `except` tuple is widened as defense-in-depth only, not as the primary fix. | 27.1 established `refuse_unsafe_destination` as the single choke point (SC-2). Handling the error downstream would re-fragment the decision across write branches — the exact "guard exists but call graph is incomplete" anti-pattern the review named. |
| D-02 | WR-05: which exit code? | **Reuse the existing unsafe-destination refusal exit code** (the one `refuse_unsafe_destination` already raises through), not a new one. | Callers already branch on it; a new code is a CLI-contract change with no added information. |
| D-03 | WR-05: is a *non-existent* path whose parent is a directory also refused? | **No.** Only destinations that *are* (or normalize to) a directory — `"."`, `"./"`, `"a/"`, an existing directory path. A normal file destination inside an existing directory stays allowed. | That is the whole point of a destination; over-refusing would break the happy path. |
| D-04 | WR-06: return shape for the corrupted-approval case? | **The existing structured invalid result** (same shape `check_valid` already returns for stale/mismatched approvals), with a distinct reason string identifying corruption. `check_valid` never raises. | WR-02 already committed to "never raises"; this completes it rather than inventing a second failure channel. Callers (`_cmd_apply`, exit 4) need no change. |
| D-05 | WR-06: how wide is the corruption table? | Invalid JSON; valid JSON that is not an object; object missing each required key **in turn**; each required key present with the **wrong type**. Table-driven (`pytest.mark.parametrize`). | Matches SC-2 verbatim; a single smoke test is precisely the happy-path-fixture defect this phase exists to close. |
| D-06 | WR-07: how is "the test fails when `flock` is removed" *proven*, not merely asserted? | **Monkeypatch `fcntl.flock` to a no-op inside a dedicated negative-control test** and assert the mutual-exclusion assertion then fails (i.e. the control test observes interleaving). The RED run and its failure message are recorded in the plan summary. | Deleting real code to prove a test is not repeatable in CI. A patched-to-no-op negative control is the executable form of "would this test fail if the fix were reverted?". |
| D-07 | WR-07: what does the positive test assert? | **Observed mutual exclusion** — two concurrent apply attempts against the same batch, with the critical section instrumented so overlap is detectable. Not the existence of the `.lock` file. | The `.lock` sidecar is created by `open()`; asserting its existence tests nothing about locking. |
| D-08 | Does this phase touch the constitution plane? | **Not expected.** WR-05 is refused by code, not by tightening the schema `pattern` further. If a contract edit becomes necessary, it is paired with hash rebaseline + derived regeneration + human ratification in one atomic commit. | 27.1-03 already tightened `manifest.schema.json`; `"."` is legitimately *shaped* like a relative path — the defect is that the applier does not check what it resolves to. Keeping the fix in code avoids a second constitution-plane round trip for a non-schema problem. |
| D-09 | Plan/wave shape? | **2 plans, 1 wave (parallel — no file overlap).** Plan 01 = WR-05 + WR-06 (both in `tools/adoption_apply/`, but distinct modules: the destination guard vs. `approval.py`); Plan 02 = WR-07 test rewrite (tests only). If planning finds file overlap between 01 and 02, serialize instead. | Small, well-bounded phase; the review already did the diagnosis. |

</decisions>
