## Critical

### CR-01: `check_valid` still raises on a non-UTF-8 `approval.json` — WR-06's off-table corruption shape

**File:** `tools/adoption_apply/approval.py:188,195` · table at `tools/adoption_apply/tests/test_approval_invalidation.py:257-268`

**Issue:** The catch tuple is `(FileNotFoundError, OSError, json.JSONDecodeError, KeyError, TypeError)`. When `path.read_bytes()` returns bytes that are not decodable UTF-8, `json.loads` raises **`UnicodeDecodeError`** — which subclasses `UnicodeError` → `ValueError`, and is neither `JSONDecodeError` nor `OSError`. Verified:

```
>>> json.loads(b'{"draft_hash": "\xc3\x28"}')
UnicodeDecodeError   # caught by check_valid tuple? False
```

`CORRUPT_APPROVAL_CASES` has four byte-literal rows (`b"{not valid json"`, `b"[1, 2, 3]"`, `b'"a bare string"'`, `b"42"`) — all valid ASCII. A truncated write, a disk-corrupted block, or a UTF-16 write are exactly the "unreadable/malformed stored approval" the docstring now promises to absorb. The escape lands at `cli.py:148`, whose `check_valid` call has no `try`, so `adopt apply` emits a traceback instead of the documented **exit 4**. That is verbatim the WR-06 defect the phase was opened to close, and the SC-2 corruption table is what should have caught it.

**Fix:** Decode explicitly and add the class, so the failure is on the parse, not on an implicit decode:

```python
    try:
        stored = json.loads(path.read_bytes().decode("utf-8"))
        ...
    except (OSError, json.JSONDecodeError, UnicodeDecodeError, KeyError, TypeError) as exc:
```

(`FileNotFoundError` is redundant — it is an `OSError` subclass; the mutation run confirms removing it changes nothing.) Add a `CORRUPT_APPROVAL_CASES` row `("invalid_utf8", b'{"draft_hash": "\xc3\x28"}')` and, ideally, a UTF-16-with-BOM row — note that `json.loads` *succeeds* on BOM'd UTF-16 via `detect_encoding`, so an explicit `.decode("utf-8")` also closes a silent encoding-sniffing path that §4.3 byte hygiene would not sanction.

## Warnings

### WR-01: the root-equality guard is dead under the test table — deleting it leaves the suite green

**File:** `tools/adoption_apply/apply.py:158-162` · table at `tools/adoption_apply/tests/test_constitution_refusal.py:186-198`

**Issue:** Mutation-verified: removing the entire `if target_path == Path(target_root).resolve():` block leaves **91 passed**. Every row grouped under `# (a) resolves to the root itself` — `"."`, `"./"`, `""` — is intercepted by the *earlier* structural `segments[-1] in ("", ".")` check and never reaches this branch:

```
'.'  -> '.' names a directory, not a file (its last path segment is empty or '.')
'./' -> './' names a directory, not a file ...
''   -> '' names a directory, not a file ...
```

The only spelling that actually reaches the branch is a **symlink that resolves to the target root**, which is absent from `DIRECTORY_SHAPED_DESTINATIONS`:

```
'selflink' -> 'selflink' resolves to the target root itself — a destination must be a proper descendant
```

The docstring's step-4 rationale ("whose `"."` result for a root-equal path matches no constitution glob and is exactly what let `"."` through") is now historically true but no longer describes what this branch defends: `"."` is stopped two checks earlier. This is SC-4's own anti-pattern reproduced inside SC-4's phase — a control whose test rows all land on a different control.

**Fix:** Add a symlink row to the table, so the branch is the thing under test:

```python
def test_refuse_unsafe_destination_rejects_symlink_to_root(tmp_path):
    os.symlink(str(tmp_path), str(tmp_path / "selflink"))
    with pytest.raises(apply.PathEscapeError, match="target root itself"):
        apply.refuse_unsafe_destination("selflink", tmp_path)
```

and tighten the existing rows with `match=` so each asserts *which* guard fired rather than only that the destination is quoted in the message.

### WR-02: a destination whose parent chain is an existing FILE still leaks a raw `FileExistsError`

**File:** `tools/adoption_apply/apply.py:140-171` (guard), `apply.py:183` (`mkdir`), `tools/adoption_apply/cli.py:195-203` (except tuple)

**Issue:** `refuse_unsafe_destination("AGENTS.md/evil.txt", root)` — where `root/AGENTS.md` is an existing file — **passes every check** and returns a path. It is not absolute, has no `..`, its last segment is `evil.txt`, it does not resolve to the root, and `is_dir()` is `False` because the parent is a file. `apply_disposition` then reaches `atomic_create` → `path.parent.mkdir(parents=True, exist_ok=True)`:

```
guard PASSED -> /.../tmp.../AGENTS.md/evil.txt
apply raised: FileExistsError | [Errno 17] File exists: '/.../AGENTS.md'
```

`FileExistsError` is not in `cli.py`'s except tuple (which gained `IsADirectoryError` and `CollisionError` but not this), so the CLI leaks a traceback — the identical shape of SC-1's promise ("never a traceback") and of WR-05 itself, one path class over. `NotADirectoryError` is the sibling on Linux and is likewise unnamed.

**Fix:** Extend the choke point rather than the except tuple (D-01's own principle — refuse before touching the filesystem):

```python
    for ancestor in list(target_path.parents):
        if ancestor == Path(target_root).resolve():
            break
        if ancestor.exists() and not ancestor.is_dir():
            raise PathEscapeError(
                f"'{destination}' has an existing non-directory ancestor '{ancestor.name}' — "
                "refusing the write."
            )
```

and add `("parent_is_file", "AGENTS.md/evil.txt")` to `DIRECTORY_SHAPED_DESTINATIONS` (with the ancestor file created by the test). Add `FileExistsError`/`NotADirectoryError` to the CLI backstop tuple for defense in depth.

### WR-03: the "Never raises" docstring is false on two more paths inside the widened `try`

**File:** `tools/adoption_apply/approval.py:179-181, 192-193`

**Issue:** The new docstring states flatly "Never raises". Beyond CR-01, two callees inside the `try` raise classes the tuple does not name:

- `_current_git_ref(repo_root)` raises **`AdoptionApprovalRefused`** (`approval.py:81`) when `git rev-parse HEAD` returns non-zero — e.g. `--repo-root` pointing at a non-repo or a repo with no commits.
- `_current_task_revision(task_dir)` → `show()` → `_read_state()` → `_validate_state()` raises **`TaskControlError`** on a missing or schema-invalid `state.json`.

Both propagate out of `check_valid` into the un-`try`'d call at `cli.py:148`. A caller reading "Never raises" and relying on it — which `_cmd_apply` does structurally — is misinformed.

**Fix:** Either narrow the promise in the docstring to "never raises on a malformed *approval document*; environment faults (`AdoptionApprovalRefused`, `TaskControlError`) still propagate", or catch them and return `False`. Prefer narrowing the docstring — see WR-04; silently absorbing a broken task state is worse.

### WR-04: the widened `try` spans callees whose failures should surface, not be reported as "approval invalid"

**File:** `tools/adoption_apply/approval.py:187-195`

**Issue:** The `try` now wraps `_recompute_draft_hash`, `_current_task_revision`, and `_current_git_ref` in addition to the parse and the subscripts. `KeyError` and `TypeError` are broad enough that a genuine defect *outside* the approval document is misclassified:

- `show(task_dir)["revision"]` — if `tools.task_control` ever returns a state dict without `"revision"` (a real bug in the CAS layer, or a schema change), the `KeyError` is swallowed and reported to the operator as "this approval is stale, re-promote", which is untrue and unactionable.
- Likewise any `TypeError` raised inside `_recompute_draft_hash`.

The mutation table confirms `KeyError` and `TypeError` are load-bearing *for the approval-document rows* — the problem is scope, not membership.

**Fix:** Narrow the `try` to just the parse and the three subscript reads; hoist the three recomputations out:

```python
    try:
        stored = json.loads(path.read_bytes().decode("utf-8"))
        expected = (stored["draft_hash"], stored["task_revision"], stored["git_ref"])
    except (OSError, json.JSONDecodeError, UnicodeDecodeError, KeyError, TypeError) as exc:
        print(f"approval.json unusable for batch '{batch_id}' at {path}: {type(exc).__name__}",
              file=sys.stderr)
        return False
    try:
        draft_hash = _recompute_draft_hash(_batch_dir(task_dir, batch_id))
    except OSError:
        return False   # WR-02's original, intentional coverage
    return expected == (draft_hash, _current_task_revision(task_dir), _current_git_ref(repo_root))
```

This keeps every currently-passing corruption row green while letting a real task-state bug crash loudly.

### WR-05: the CLI test's diagnostic assertion is vacuous for the `"."` row

**File:** `tools/adoption_apply/tests/test_cli.py:637-641`

**Issue:** `assert destination in result.stderr` is the row's only check that the refusal is the *right* refusal. For `destination == "."`, the substring `"."` appears in essentially any stderr this CLI can emit — the prefix `tools.adoption_apply apply:` alone satisfies it, as does any filesystem path or sentence-ending period. So the `root_dot` row would still pass if the WR-05 guard were reverted: with the guard gone, `"."` reaches the `create` branch, `target_path.exists()` is true (it is the root directory), `ConcurrentDriftError` is raised, and the CLI exits 1 with a stderr containing a dot. Exit code 1, no `Traceback`, non-empty stderr, dot present — all four assertions hold for the *wrong* reason. Only the `trailing_slash` row and the final `not (apply_target / "newdir").exists()` carry real signal.

**Fix:** Assert the refusal's identifying text, not the destination substring:

```python
        assert "names a directory" in result.stderr or "target root itself" in result.stderr, case_name
```

and split the two rows into `pytest.mark.parametrize` cases so a failure names which spelling regressed instead of aborting the shared loop.

## Advisory

### AD-01: the negative control's overlap is barrier-manufactured, with a timeout that fails as an error rather than an assertion

**File:** `tools/adoption_apply/tests/test_atomic_apply.py:280-284, 366-388`

`barrier.wait(timeout=_BARRIER_TIMEOUT_SECONDS)` raises `threading.BrokenBarrierError` on timeout. That propagates out of `_instrumented` → `future.result()` → the test **errors** before reaching `pytest.raises(AssertionError)`. So on a loaded CI box the negative control's failure mode is an unrelated-looking `BrokenBarrierError` rather than a legible "the control is no longer detected". Worth a comment naming that, or wrapping the barrier wait so a timeout surfaces as an explicit `pytest.fail("barrier timed out — flock may still be active")`. Symmetrically, the positive test's reliance on a 0.2 s dwell to force overlap is timing-dependent in the other direction, though `test_marker_merge_acquires_exclusive_flock` provides a timing-independent backstop (and the mutation run shows both go red, so this is a legibility concern, not a correctness one).

### AD-02: `monkeypatch.setattr(apply.fcntl, "flock", ...)` mutates the global stdlib module

**File:** `tools/adoption_apply/tests/test_atomic_apply.py:377, 400-402`

`apply.fcntl` *is* the singleton `fcntl` module, so patching its `flock` attribute disables/instruments locking process-wide for the duration — including `tools/adoption_apply/batch.py::update_status` and `tools/task_control/manager`'s CAS lock. `monkeypatch` restores it, and pytest is single-threaded here, so this is safe today; it becomes a cross-test hazard under `pytest-xdist --dist loadfile` with threads, or if a fixture ever spawns background work. Consider patching a module-local indirection (`apply._flock = fcntl.flock`) instead.

### AD-03: D-04 deviation — `check_valid` returns a bare `bool` + a `print`, not "a structured invalid result with a distinct reason string"

**File:** `tools/adoption_apply/approval.py:173-210` · `27.2-CONTEXT.md` D-04

D-04 specified "the existing structured invalid result … with a distinct reason string identifying corruption". The implementation keeps the `-> bool` signature (which was in fact always a bool — D-04's premise was wrong) and emits the reason via `print(..., file=sys.stderr)` from library code. That is a defensible resolution, but the deviation is undocumented in either SUMMARY, and printing from a library function is a different contract than returning a reason. Also: the comment above the `print` asserts a no-content-leak property ("names the path and the exception class ONLY — never the file's contents") that **no test verifies** — none of the corruption rows use `capsys`. Add one `capsys` assertion that the corrupt bytes do not appear in stderr, or the guarantee is a comment, not a control.

### AD-04: `CollisionError` now maps to exit 1, contradicting `apply.py`'s stated propagation policy

**File:** `tools/adoption_apply/cli.py:201` vs. `tools/adoption_apply/apply.py:356-359`

`apply_manifest`'s docstring classifies `CollisionError` (alongside `ConcurrentDriftError`, `UnknownDispositionError`) as an "integrity fault, not a routine per-destination outcome" that "propagates immediately". The CLI now flattens it to the same exit 1 as a routine path refusal, so an operator cannot distinguish "you asked for something unsafe" from "the target tree changed underneath the apply". Not wrong — `ConcurrentDriftError` was already in the tuple — but the docstring should stop claiming a distinction the CLI no longer preserves.

### AD-05: a directory-shaped row now aborts a manifest mid-apply, leaving earlier writes committed

**File:** `tools/adoption_apply/apply.py:368-380`

`apply_manifest` buckets only `ConstitutionRefusal` per-record; `PathEscapeError` propagates and terminates the loop. Pre-existing behaviour, but WR-05 materially widens what raises `PathEscapeError` from "hostile spelling" to "a plausible manifest row asking for a directory" — so partial application is now reachable from an honest mistake. Since records are applied in sorted-destination order, the surviving state is deterministic but arbitrary. Consider bucketing `PathEscapeError` into `refused` alongside `ConstitutionRefusal`, or documenting the partial-apply semantics in `apply_manifest`'s docstring.
