## Summary

I re-derived all seven `27-REVIEW.md` findings against the shipped code, live-tested the new
`refuse_unsafe_destination` choke point with an adversarial input set (unicode NFD, trailing
dot/space, empty string, `.` alone, Windows-style separators, very long paths, symlink swaps,
resolved-through-symlink-into-`contracts/`), diffed the D-01-protected Phase 27 tests against
their pre-phase-27.1 originals, verified the derived-plane artifacts (`contracts/.hashes/manifest.json`,
`.memory/derived/contracts-index.md`, the `memory_regen` snapshot) actually match a hash
recomputation rather than being hand-edited, and ran the full workspace suite (1129 passed,
matches the phase's own claim).

**The three CR-01/CR-02/CR-03 findings are genuinely fixed, not merely test-shaped.** I confirmed
this by reverting each guard mentally and tracing what test would catch the regression:
`refuse_unsafe_destination` is the single call site in `apply_disposition` (verified: `grep -n
"refuse_if_constitution\|refuse_if_outside_root\|refuse_unsafe_destination"` shows
`apply_disposition` calls only the new choke point, and both older primitives are reused
*inside* it rather than bypassed); `_cmd_apply` calls `check_valid` as its literal first
statement, before the manifest is even read off disk; the `--repo-root` flag is `required=True`
with no permissive default. The symlink-read defense (`_read_target_no_symlink`/`O_NOFOLLOW`) is
checked at actual syscall time inside the lock, which correctly defeats the TOCTOU window between
`refuse_unsafe_destination`'s check-time `resolve()` and the marker-merge read — I verified this
structurally (O_NOFOLLOW re-checks regardless of what the earlier `resolve()` saw) and via the
existing `test_marker_merge_refuses_symlink_read` test's live pass/fail behavior.

However, adversarial probing surfaced **two new, unaddressed, reproducible defects** in the exact
choke points this phase built, both crashes rather than clean refusals — undermining the phase's
own stated goal ("a hostile or malformed manifest is refused cleanly, never an unhandled
traceback"). I verified both live against the shipped code (commands below), not merely by
reading the source:

1. A `destination` of `"."` (a single dot) passes both `manifest.schema.json`'s new WR-03
   `pattern` constraint *and* `refuse_unsafe_destination` cleanly (resolves to `target_root`
   itself, which is trivially "inside root" and matches no constitution glob), then crashes
   `apply_disposition`'s `create` branch with an unhandled `IsADirectoryError` when it calls
   `_existing_hash` on a directory. Not caught by `cli.py`'s except tuple. (WR-05, new)
2. `approval.check_valid` still raises uncaught (`json.JSONDecodeError`, `KeyError`) on a
   corrupted/malformed `approval.json` — the WR-02 fix only wrapped the
   `_recompute_draft_hash(batch_dir)` call, not the `json.loads(path.read_bytes())` /
   `stored["draft_hash"]` reads that happen before and after it. Both fail *closed* (no write
   happens), so this is not a security bypass, but it violates `check_valid`'s own docstring
   contract ("no partial credit — any single mismatch returns `False`") and crashes `_cmd_apply`
   with a raw traceback instead of the clean exit-4 message every other no-approval path gets.
   (WR-06, new)

I also found one testing-rigor gap in the WR-01 (marker-merge lock) regression test, and two
lower-severity defense-in-depth gaps (TOCTOU on parent-directory symlink swaps; the approval gate
living only in `cli.py`, not `apply.py` itself). All are detailed below. None of the original
seven findings are reopened; none of Phase 27's `D-01`-protected tests were touched.

## Warnings

### WR-05: `destination: "."` bypasses both the schema pattern and `refuse_unsafe_destination`, crashing `apply_disposition` with an unhandled `IsADirectoryError`

**File:** `tools/adoption_apply/apply.py:109-143` (`refuse_unsafe_destination`), `291-297`
(`apply_disposition`'s `create` branch); `contracts/harness/adoption/manifest.schema.json:57-62`
(`dispositionRecord.destination` pattern)

**Issue:** Verified live:

```python
>>> Path(target_root) / "."   # resolves to target_root itself
>>> apply.refuse_unsafe_destination(".", target_root)   # does NOT raise
>>> apply.apply_disposition({"destination": ".", "disposition": "create"}, target_root, payload=b"x")
IsADirectoryError: [Errno 21] Is a directory: '<target_root>'
```

`"."` has length 1 (passes `minLength: 1`) and contains no `..` segment (passes WR-03's new
`pattern`), so it validates cleanly against `manifest.schema.json`. At runtime,
`refuse_unsafe_destination`'s structural pre-check only rejects an absolute path or a literal
`".."` segment — `"."` is neither. `(Path(target_root) / ".").resolve(strict=False)` collapses to
`target_root` itself, which trivially passes `refuse_if_outside_root` (it *is* the root) and
whose relative-to-itself path (`"."`) matches no `CONSTITUTION_GLOBS` entry. `target_path` is
therefore `target_root`, which always exists (it's a directory) — `apply_disposition`'s `create`
branch calls `_existing_hash(target_path)` (`tools/adoption_scan/destinations.py:277-282`), which
does `path.open("rb")` on a directory, raising `IsADirectoryError`. This propagates uncaught
through `apply_manifest` (not one of the exceptions bucketed into `"refused"`) and out of
`cli.py`'s except tuple (which lists `ConstitutionRefusal, ConcurrentDriftError,
UnknownDispositionError, PathEscapeError, SymlinkRefusal` — not `IsADirectoryError`), producing a
raw Python traceback on stderr. This directly contradicts this phase's own stated WR-04/BLOCKER
goal that a hostile-destination manifest "surfaces as the same clean, documented nonzero exit
every other apply-time failure gets, never an unhandled traceback." No test in
`test_manifest_schema_conformance.py` or `test_constitution_refusal.py`/`test_atomic_apply.py`
exercises `"."` or `""` as a destination value (only real/synthetic multi-segment paths and the
`HOSTILE_DESTINATIONS`/`PATH_ESCAPE_KINDS` tables, none of which include a bare `"."`).

**Fix:** In `refuse_unsafe_destination`, reject a `destination` that resolves to `target_root`
itself (i.e., `target_path == Path(target_root).resolve()`), not just paths that resolve outside
it — a destination must be a proper descendant of `target_root`, never the root itself:
```python
target_path = (Path(target_root) / destination).resolve(strict=False)
refuse_if_outside_root(target_path, target_root)
if target_path == Path(target_root).resolve():
    raise PathEscapeError(f"'{destination}' resolves to target_root itself — not a valid destination.")
```
Add `"."`/`""`/`"./"` to the schema's forbidden set too (the pattern's `(?!/)` /
`\.\.` checks don't cover a bare `.`), e.g. `(?!\.?/?$)` prepended to the existing lookaheads —
this is a `contracts/` change and therefore human-ratified per this repo's own constitution-plane
rule, flagged here for the record. Add a regression test asserting `destination: "."` is refused
cleanly (`PathEscapeError`, not `IsADirectoryError`) by both the schema and the runtime choke
point.

### WR-06: `approval.check_valid` still raises uncaught on a corrupted `approval.json`, only the missing-draft-artifact case was fixed

**File:** `tools/adoption_apply/approval.py:172-193`

**Issue:** WR-02's fix wraps only `_recompute_draft_hash(batch_dir)` in
`try/except (FileNotFoundError, OSError): return False` (line 183-188). The two other unguarded
reads in the same function are not covered. Verified live:

```python
>>> (bd / "approval.json").write_text("{not valid json", encoding="utf-8")
>>> approval.check_valid(task_dir, "b1", repo_root)
json.decoder.JSONDecodeError: Expecting property name enclosed in double quotes: ...
```
```python
>>> (bd / "approval.json").write_text(json.dumps({"batch_id": "b1"}))  # missing draft_hash etc.
>>> approval.check_valid(task_dir, "b1", repo_root)
KeyError: 'draft_hash'
```

Both a malformed `approval.json` (line 181: `stored = json.loads(path.read_bytes())`) and one
missing a required key (line 189-192: `stored["draft_hash"]`/`stored["task_revision"]`/
`stored["git_ref"]`) raise uncaught, contradicting the function's own docstring: "No partial
credit — any single mismatch returns `False`." `cli.py`'s `_cmd_apply` calls `check_valid` with no
surrounding `try/except` (per 27.1-02's own design — the call is meant to be a clean boolean
gate), so either exception crashes `_cmd_apply` with a raw traceback instead of the clean exit-4
"no valid approval" message every other no-approval path already gets. This fails *closed* (no
write happens before the crash), so it is not a security bypass, but it is a real robustness gap
in the exact function this phase's CR-03 fix depends on, and it is not covered by
`test_valid_false_on_missing_draft_artifact` (which only tests a missing *draft* file, not a
corrupted or incomplete `approval.json` itself).

**Fix:** Widen the guarded region to cover the whole read-and-compare, or add a second
`try/except (json.JSONDecodeError, KeyError): return False` around the `stored = json.loads(...)`
line and the final boolean expression:
```python
try:
    stored = json.loads(path.read_bytes())
    draft_hash = _recompute_draft_hash(batch_dir)
    return (
        stored["draft_hash"] == draft_hash
        and stored["task_revision"] == _current_task_revision(task_dir)
        and stored["git_ref"] == _current_git_ref(repo_root)
    )
except (FileNotFoundError, OSError, json.JSONDecodeError, KeyError):
    return False
```
Add a regression test seeding a corrupted/incomplete `approval.json` and asserting `check_valid`
returns `False` rather than raising.

### WR-07: `test_concurrent_marker_merge_does_not_lose_writes` does not actually prove the `fcntl.flock` lock is exercised — it would still pass if the `flock()` call itself were silently removed

**File:** `tools/adoption_apply/tests/test_atomic_apply.py:265-297`

**Issue:** The test's primary assertion is `lock_path.is_file()` — but `lock_path` is created
merely by `lock_path.open("a+b")` (line 248 of `apply.py`), independent of whether
`fcntl.flock(lock.fileno(), fcntl.LOCK_EX)` is ever actually called. If a future edit removed the
`fcntl.flock(...)` line but left the `with lock_path.open("a+b") as lock:` context manager intact,
this test would still pass (the sidecar file is still created by the `open()` call alone), and the
secondary content-corruption assertions (`final_text.count("## Block A") <= 1` etc.) are not
reliably RED under thread-scheduling non-determinism even without a lock — the plan's own
documentation acknowledges this ("if the race is not reliably reproducible... prefer the
structural assertion"). The net effect: this is the *only* regression test for WR-01
(the unlocked read-modify-write CR that motivated this whole sub-fix), and it does not actually
exercise whether `fcntl.flock` is functioning, only whether a same-named file exists on disk.

**Fix:** Assert the lock is actually acquired/contended, e.g. by holding the lock in the test
process and asserting a second `_apply_marker_merge` call blocks until released (a
`threading.Event`-gated fake merge, or asserting `fcntl.flock(lock.fileno(), fcntl.LOCK_EX |
fcntl.LOCK_NB)` raises `BlockingIOError` while `_apply_marker_merge` holds the lock mid-merge via
a monkeypatched `merge_settings`/`splice_managed_block` that blocks on an event). At minimum,
monkeypatch `fcntl.flock` with a spy and assert it was actually called with `LOCK_EX` before the
read, to structurally prove the call site still exists (this closes the "silently removed" gap
without needing a reliable interleaving reproduction).

### WR-08: No defense against a parent-directory symlink swap between `refuse_unsafe_destination`'s check-time `resolve()` and the actual write

**File:** `tools/adoption_apply/apply.py:109-143` (`refuse_unsafe_destination`), `146-178`
(`atomic_create`), `232-261` (`_apply_marker_merge`)

**Issue:** The final path component is protected against a symlink swap at write time: `create`'s
`os.link` atomically fails with `FileExistsError` if the destination already exists in any form
(regular file or symlink) — safe by construction; marker-merge's read side re-checks
`O_NOFOLLOW` at actual syscall time inside the lock, independent of the earlier `resolve()` —
also safe. But nothing re-checks a **parent directory** component between
`refuse_unsafe_destination`'s `Path.resolve(strict=False)` (which only actually resolves symlinks
for path components that exist *at check time*) and the later `path.parent.mkdir(parents=True,
exist_ok=True)` / `tempfile.mkstemp(..., dir=path.parent)` calls inside `atomic_create`/
`_atomic_replace`. If an intermediate directory component of `destination` does not yet exist at
check time (so `resolve(strict=False)` cannot resolve a symlink that doesn't exist yet), and an
attacker races a symlink into place at that path between the check and the `mkdir`/`mkstemp`
calls, the write can land outside `target_root` despite `refuse_unsafe_destination` having
"passed" the destination. This requires local filesystem race-window write access to the target
tree during a single `apply` invocation — a narrower threat than CR-01/CR-02's manifest-content
attacker, but it is the literal "symlink swapped between check and write" scenario this phase's
own `27.1-RESEARCH.md` threat model discusses only for the *final* path component (T-27.1-03/04),
not for parent directories.

**Fix:** Lower severity, defense-in-depth only — document this as an accepted residual risk (the
threat model already implicitly assumes no concurrent hostile filesystem actor racing the same
`apply` invocation), or harden `atomic_create`/`_apply_marker_merge`'s parent-directory creation
to use `os.open(..., os.O_NOFOLLOW | os.O_DIRECTORY)` walks rather than `Path.mkdir`/`mkstemp`
convenience calls, if this threat is judged in-scope.

## Info

### IN-01: The ADOPT-06 approval gate lives only in `cli.py`, not in `apply.py` itself — inconsistent with the constitution-refusal control's own defense-in-depth posture

**File:** `tools/adoption_apply/apply.py` (no `check_valid` reference anywhere in this module),
`tools/adoption_apply/cli.py:148-154`

**Issue:** `refuse_unsafe_destination` lives inside `apply.py` itself specifically so that *any*
caller of `apply_manifest`/`apply_disposition` — not just `cli.py`'s `apply` subcommand — is
structurally protected (this is `apply.py`'s own stated design rationale, restated in its module
docstring). `check_valid`, by contrast, is enforced *only* at the `cli.py` boundary. Any code that
imports `tools.adoption_apply.apply.apply_manifest` directly (a test harness, a future script, an
agent skill that shells out to the module rather than the CLI) bypasses the human-ratification
gate entirely, even though nothing else about `apply.py`'s threat model changed. This is not a
regression from this phase (CR-03's own fix was scoped to "wire `check_valid` into `_cmd_apply`"),
but it is worth flagging: the module-level defense-in-depth guarantee `apply.py`'s docstring
claims ("independent of any Claude hook... any caller") does not, in fact, extend to the approval
gate the way it does to the destination-safety gate.

**Fix:** No code change required for this phase's stated scope. Consider, in a future pass,
moving the `check_valid` precondition into `apply_manifest` itself (accepting an optional
`task_dir`/`batch_id`/`repo_root` triple) so the guarantee is structural at the same layer as
`refuse_unsafe_destination`, rather than trusting every future caller to remember the CLI wrapper.

### IN-02: `fcntl.flock`'s NFS behavior is not addressed by the WR-01 fix or its threat model

**File:** `tools/adoption_apply/apply.py:246-249`

**Issue:** `fcntl.flock` is advisory and, depending on the NFS version/lock daemon configuration,
may not provide cross-process mutual exclusion over an NFS-mounted target tree — a pre-existing
limitation this phase inherits verbatim from `batch.py::update_status`'s idiom (not new), but the
27.1-01 threat model (`T-27.1-02`) does not mention it as an accepted risk the way `T-27.1-04`
explicitly documents the `os.replace`-on-symlink acceptance. Not a regression; recorded for
completeness since the review context asked about NFS/`fcntl` availability explicitly.

**Fix:** No code change required; consider adding a one-line acceptance note to the threat model
mirroring `T-27.1-04`'s style, since this precedent already exists in the same document.
