## Summary

Phase 29 is the **thinnest** phase in v2.3 by new-code volume and the **highest** by integration risk. There is one genuinely new artifact pair (`harness/commands/docs-update.md` + `harness/skills/docs-upkeep/SKILL.md`), for which Phase 27-06 is a line-by-line working template — the same shape, in the same milestone, four commits ago. There is **zero** new CI machinery: every item in SC-4's fan-in list already exists as a job or as a test inside `core-suite`, except `docs-guard` (Phase 28's) and `git diff --check` (which has never been a CI job in this repo — it is a *verification-time* command, `24-VERIFICATION.md:30,84`).

The phase's real work is three structural questions that a SKILL.md body cannot answer:

1. **The five exclusions must be code, not prose.** A skill that says "don't edit accepted ADRs" is exactly the defect class Phase 27.1 SC-3 caught — `brownfield-adoption/SKILL.md`'s Stage-5 claim was untrue for the shipped code (`ROADMAP.md:641`). The exclusion must be a pure function in `tools/docs_guard/` whose deletion turns a data-based test RED.
2. **The ledger is the greenness authority, and an agent must not be able to write it.** Phase 28's D-04 disposition-coherence control does **not** close this: an agent that invents a `[[binding]]` and pastes a matching `reviewed-no-change` row with the exact live digests produces a *consistent-by-construction* FRESH state with no git history to contradict it. `docs/.docs-review-ledger.toml` is **not** on the constitution plane (`contract_guard.py:43` — `contracts/**`, `docs/adr/**`, `golden/**` only), so nothing currently refuses that write. This is the phase's single most important finding.
3. **The queue is gitignored, so it cannot be `/docs-update`'s data source.** On a fresh clone `.memory/derived/docs-staleness.md` does not exist. The drive loop must invoke the guard; the queue is a SessionStart *pointer*, not an interface.

**Primary recommendation:** Author `/docs-update` as a fixed-argv macro over `python -m tools.docs_guard` (never over the queue file), add one `exclusions.py`-shaped pure function to `tools/docs_guard/` that imports `DERIVED_GLOBS` and `CONSTITUTION_GLOBS` rather than retyping them, extend `refuse_unsafe_destination` (`apply.py:109`) with a narrow ledger refusal so `/adopt` can write the registry but never the ledger, seed 6–8 bindings by an ordinary reviewed human commit, and close the milestone with `/gsd:audit-milestone` + `/gsd:complete-milestone` following the `v2.1-MILESTONE-AUDIT.md` shape. **No new CI job. No new persona. Zero new dependencies.**

## 2 — How `/docs-update` consumes Phase 28's output

### 2.1 It must invoke the guard, not read the queue. The fresh-clone case settles it.

**Do not read `.memory/derived/docs-staleness.md`.** Three independent reasons, all verified:

1. **Fresh clone / fresh CI checkout.** `.gitignore:23` is the contents-form `.memory/derived/*` with a single re-inclusion `!.memory/derived/contracts-index.md` at `.gitignore:24`. The queue file is therefore **never in a clone**. A `/docs-update` that reads it would, on a fresh clone, either crash or — far worse — read *nothing* and report "no work", which is a false green.
2. **Staleness.** The queue is regenerated by `/refresh-memory` (`refresh-memory.md`) at session boundaries. Between regenerations it is arbitrarily old. A drive loop bound to it is non-deterministic with respect to the working tree.
3. **Single-source rule.** The repo's standing rule is one implementation per derived fact (`docs-sync.md:12-16`: "a second read/hash impl could silently disagree with the drift gate"; `28-RESEARCH.md:336`: "A second digest implementation"). The guard is the authority; the queue is a *rendering* of it.

The queue's role is **exactly and only** the SessionStart pointer path: `docs_staleness.render/write` → `.memory/derived/docs-staleness.md` → `inject.assemble()`'s one droppable conditional line (`28-CONTEXT.md:38` D-11; `inject.py:157-188`). `/docs-update` is a peer consumer of the *guard*, not a consumer of the queue.

**Recommended command body shape** (fixed argv, `$ARGUMENTS` positional — never woven into a constructed shell string, the invariant `adopt.md:83-86` states explicitly):

```
!`uv run python -m tools.docs_guard $ARGUMENTS`
```

Optionally a second sub-verb line refreshing the queue afterwards, `!`uv run python -m tools.memory_regen.docs_staleness``, so the SessionStart pointer reflects the post-edit state. That invocation lives in `docs-update.md`, which is **not** covered by `_ALLOWED_TOOL_MODULES`.

### 2.2 Exit-code routing — what the loop does with 0 / 1 / 3

Bound to `28-CONTEXT.md:32` (D-05) and `28-RESEARCH.md:164-172`:

| Exit | Meaning | `/docs-update` action | Precedent |
|---|---|---|---|
| **0** | No `BROKEN`, no `STALE_REQUIRED`, uncovered within ratchet | **Stop. Report clean.** `STALE_ADVISORY` items may be listed on stderr as optional work; the loop must NOT auto-open advisory work — that is what makes it *bounded*. | `drift.py:370-390` 0/1 convention |
| **1** | ≥1 `BROKEN` / `STALE_REQUIRED`, or uncovered regression | **The drive loop's only working state.** For each reported binding, draft EITHER a bounded edit to the bound target doc, OR the exact review disposition, then route to `/review` + `/verify-work`. Never write the ledger (§4). | `drift.py` exit 1 |
| **3** | **Registry invalid** (path escape, duplicate id, empty required selector, derived/reference target, illegal ADR disposition) | **Refuse to draft anything.** Print the registry diagnostic and stop. The operator action is *fix `docs/doc-dependencies.toml`*, not *edit a doc* — drafting a doc edit here would be acting on an unvalidated registry. | `approve.py` / `AdoptionApprovalRefused` → `cli.py:26` exit 3; `StranglerRefused` |
| 2 | argparse usage error (stdlib default) | Pass through unchanged; do not reuse for domain meaning. | `28-RESEARCH.md:170` |

**Bounded-ness is a property of exit-1 handling, and it must be stated in the SKILL body AND enforced by the command's argv shape.** The loop is bounded because: (a) it acts only on the guard's enumerated `BROKEN`/`STALE_REQUIRED` set, which is finite and deterministic; (b) it never expands scope to `UNCOVERED` documents (raising the ratchet is a human edit — `28-CONTEXT.md:33` D-06); (c) it never chases `STALE_ADVISORY`; (d) it makes exactly one pass — re-running is idempotent because the guard is read-only.

### 2.3 Anti-double-report with the leading gates

Phase 28's D-13 (`28-CONTEXT.md:40`) has the guard report `SUPPRESSED (contract-drift leading)` for a binding whose source is a currently-drifted contract. `/docs-update` inherits this for free by reading the guard's output — **it must not re-run `contract_drift.run_gate()` itself**, and its report text must not mention contract drift (the SessionStart payload already carries a never-dropped `drift` section, `inject.py:170`).

### 3.2 The recommended mechanism

Add **one pure function** to `tools/docs_guard/` — a new `exclusions.py`, or a function on the existing `registry.py`:

```
def exclusion_reason(target: str) -> str | None
```

### 4.2 What exactly prevents it from being green — and the hole that must be closed

Greenness is decided by the **ledger**, not the registry. `28-CONTEXT.md:29` (D-02) puts it at `docs/.docs-review-ledger.toml`.

Three layers, in increasing order of load-bearing:

1. **Fail-closed by construction.** A newly proposed `severity = "required"` binding with no `[[reviewed]]` row classifies **`BROKEN`** → exit 1 (`28-RESEARCH.md:153`). An `advisory` one is `STALE_ADVISORY` → warn, also not FRESH. So a proposal alone can never be green. ✅
2. **Disposition/digest coherence (D-04).** `updated` requires a target-digest delta versus the previous committed ledger, retrieved via the `_git_show_at` shape (`drift.py:129-147`). ✅ for the `updated` path.
3. **⚠️ THE HOLE.** D-04 does **not** close `reviewed-no-change`. That disposition is *content-bound only* — it passes iff the ledger digests equal the live digests (`28-RESEARCH.md:181`). An agent that (a) writes a `[[binding]]` row and (b) writes a `[[reviewed]]` row with `disposition = "reviewed-no-change"` and the two exact live digests produces a state that is **consistent by construction**, has no previous committed row to contradict it, and classifies **FRESH**. The binding is green with no human in the loop.

   And nothing currently stops that write: `docs/.docs-review-ledger.toml` is **not** in `CONSTITUTION_GLOBS` (`contract_guard.py:43` — verified: three globs, contracts/adr/golden), **not** in `path_deny_globs` (`permission-matrix.json:27-33` — verified: those three plus `*.env`), and **not** in CODEOWNERS (`.github/CODEOWNERS:26-32` — verified: `/contracts/`, `/docs/adr/`, `/golden/`, `/approvals/`, plus two example-instance rows). And CODEOWNERS is advisory anyway — its own header says so (`.github/CODEOWNERS:7-12`).

**Recommended closure — a narrow refusal at the existing single choke point, with a data-based test.**

Add to `refuse_unsafe_destination` (`apply.py:109`) a new check, *after* the confinement steps and *beside* `refuse_if_constitution(relative.lower())` at `apply.py:169`:

```
REVIEW_LEDGER_GLOBS = ["docs/.docs-review-ledger.toml"]   # its own constant, its own exception
```

with its own diagnostic and its own exception class (e.g. `ReviewLedgerRefusal`), **not** by widening `CONSTITUTION_GLOBS`. Widening `CONSTITUTION_GLOBS` would be wrong on two counts: it is imported by `contract_guard` (`contract_guard.py:43`) and by `destinations.py:31`, so the ledger would suddenly become CODEOWNERS-gated, require `GOLDEN_APPROVE_HUMAN` for every ordinary human review commit, and the "the two gates' domains are provably disjoint" invariant (`contract_guard.py:16-20`) would need re-derivation. Keep the domains separate.

Test (RED first): a manifest whose `destination` is `docs/.docs-review-ledger.toml` — plus the spelling variants `./docs/.docs-review-ledger.toml`, `docs/../docs/.docs-review-ledger.toml`, and the case variant — is refused **before any filesystem write**, proven by a spy asserting zero `open()` / `os.link()` / `os.replace()` calls (the Phase 27.1 SC-2 idiom, `ROADMAP.md:640`).

**Also do the cheap defence-in-depth layers, in the same change:**
- `.github/CODEOWNERS`: add `/docs/.docs-review-ledger.toml @hjung3113` (advisory, but it routes the review).
- Consider adding the ledger path to `harness/permission-matrix.json` `path_deny_globs` **only after** confirming the effect on `contract_guard._on_constitution_plane` — that function feeds `CONSTITUTION_GLOBS`, not the full matrix union (`contract_guard.py:16-20`), so the matrix addition is inert for that hook and would only affect `resolve_path` consumers. **Recommend: skip it.** An inert data change that looks like a gate is worse than no change.

### 4.3 The other landmine: an agent editing `docs/doc-dependencies.toml` to *remove* an inconvenient binding

A binding that is `STALE_REQUIRED` can be made green by deleting it from the registry. That is not caught by the ledger refusal. The existing counter is the **uncovered ratchet** (`[coverage] uncovered_max`, `28-CONTEXT.md:33` D-06) — deleting a binding raises `live_uncovered`, and `live_uncovered > uncovered_max` fails. **But only if the deleted target is inside the D-07 corpus.** A binding whose target is `harness/skills/brownfield-adoption/SKILL.md` (§5) is **outside** the D-07 corpus (`docs/{tutorials,how-to,explanation}/**` + `docs/glossary.md` + root `AGENTS.md`/`CLAUDE.md` + `.memory/README.md`), so deleting it is invisible to the ratchet. **Surface this to the planner:** either extend the corpus to cover the seeded non-`docs/` targets, or add a registry-binding-count ratchet alongside the uncovered ratchet. Recommend the latter — it is one integer in the same `[coverage]` table and does not disturb Phase 28's corpus decision.

## Common Pitfalls

### P1 — The exclusion that is only prose
**What goes wrong:** `docs-upkeep/SKILL.md` says "never edit an accepted ADR"; nothing enforces it; a later agent (or a bare CLI path with no hook) does exactly that.
**Why:** identical to 27.1 SC-3 — `brownfield-adoption/SKILL.md`'s Stage-5 claim was untrue against shipped code (`ROADMAP.md:632,641`).
**Avoid:** §3.2's pure function + §3.3's data table, RED-confirmed.
**Warning sign:** the plan's verification step greps a markdown file for a phrase.

### P2 — The `reviewed-no-change` self-blessing hole
**What goes wrong:** an agent writes a binding *and* its ledger row with the exact live digests; the guard classifies FRESH; no human reviewed anything.
**Why:** D-04's coherence check binds `updated` to a target delta, but `reviewed-no-change` is content-bound only (`28-RESEARCH.md:181`), and a brand-new binding has no previous committed row.
**Avoid:** §4.2's ledger-write refusal at `apply.py:109`, plus the `checkpoint:human-verify` seeding shape in §5.4.
**Warning sign:** any plan step where an agent writes `docs/.docs-review-ledger.toml`.

### P3 — The fresh-clone false green
**What goes wrong:** `/docs-update` reads `.memory/derived/docs-staleness.md`; on a clean checkout the file does not exist (`.gitignore:23-24`); the loop reports "nothing to do."
**Avoid:** invoke `tools.docs_guard`. §2.1.
**Warning sign:** the command body names a file path under `.memory/`.

### P4 — New emitted files land untracked and `emit-drift` passes anyway
**What goes wrong:** four new files under `.opencode/` + `.claude/` are emitted but never `git add`ed; `ci.yml:213`'s bare `git diff --exit-code` cannot see them.
**Why:** carried finding, `v2.1-MILESTONE-AUDIT.md` tech_debt (15-REVIEW CR-01). The fix idiom (`git add -A` + `--cached`) already exists at `ci.yml:238-239`.
**Avoid:** explicit `git add` of all four paths + `emit-manifest.json`; verify with `git status --porcelain -- .opencode .claude`.

### P5 — `EXPECTED_SKILLS` half-widened
**What goes wrong:** the skill directory is added but `caps.py:129-144` isn't (or vice versa). Three tests fail: `test_skills.py:53`, `validate.check_skill_set` inside the emitter, `test_emit_determinism.py:99`.
**Avoid:** one change, both edits, plus the `test_coexist.py:39,64,65` command-count bump 24 → 25.

### P6 — Binding deletion as a green-making move
**What goes wrong:** a `STALE_REQUIRED` binding on `harness/skills/brownfield-adoption/SKILL.md` is deleted from the registry; the uncovered ratchet doesn't notice because that target is outside the D-07 corpus.
**Avoid:** a binding-count ratchet in `[coverage]` alongside `uncovered_max`. §4.3.

### P7 — Editing inside the HARNESS-MANAGED fence
**What goes wrong:** a drafted edit lands between `AGENTS.md:98` and `AGENTS.md:107`; the next emit reverts it and `emit-drift` reds.
**Avoid:** §5.3 — either don't seed those two files, or add a sixth `marker-managed-region` exclusion class.

### P8 — Twelve new CI jobs
**What goes wrong:** SC-4's list is read as a to-do rather than an inventory.
**Avoid:** §6's table. Net delta is zero.

## Landmines (explicit, as requested)

**Anything that would let an agent self-review a docs binding:**
1. **`reviewed-no-change` on a brand-new binding** — the D-04 coherence rule does not reach it; there is no previous committed row to contradict. §4.2. **Unmitigated today.**
2. **`docs/.docs-review-ledger.toml` is writable by every existing mechanism** — not in `CONSTITUTION_GLOBS` (`contract_guard.py:43`), not in `path_deny_globs` (`permission-matrix.json:27-33`), not in `.github/CODEOWNERS:26-32`. Verified all three.
3. **CODEOWNERS is advisory** by its own admission (`.github/CODEOWNERS:7-12`) and in a solo repo cannot be satisfied by self-review (`:14-19`). It is documentation of intent, never a gate.
4. **Deleting a binding** is an unguarded green-making move for targets outside the D-07 corpus. §4.3.

**Anything that makes `/docs-update` non-deterministic or unbounded:**
5. Reading the gitignored queue (§2.1) — value depends on when `/refresh-memory` last ran, and is absent entirely on a fresh clone.
6. Acting on `STALE_ADVISORY` or on `UNCOVERED` — advisory is warn-only, and raising the ratchet is a human edit (`28-CONTEXT.md:33` D-06). Either turns a bounded pass into an open-ended one.
7. Re-running `contract_drift.run_gate()` inside the loop — a git subprocess plus a full recompute, and it double-reports (`28-CONTEXT.md:40` D-13).
8. Any wall-clock in a new committed artifact — `test_inject_determinism.py:70-85` is a **static token scan**; an unused `import datetime` in `inject.py` fails it.

**Any exclusion expressed only as prose:**
9. The `docs-upkeep` SKILL body. §3.1/P1. The precedent that this actually happens is 27.1 SC-3.
10. `docs/glossary.md:3` self-declares "plane: constitution (human-owned)" — **prose only**; it is not in `CONSTITUTION_GLOBS` and is a perfectly legal binding target. Don't let the prose be mistaken for a gate in either direction.

**Any new CI job that double-reports:**
11. `git diff --check` as a job — `polyglot_lint` (commit gate) + `format-on-write` already cover BOM/CRLF/trailing whitespace. §6.
12. A "docs" job separate from Phase 28's `docs-guard`. One gate, one job.
13. Re-running `uv run pytest` in a new job — `core-suite` (`ci.yml:170-178`) already runs the whole thing.

**The fresh-clone case for a gitignored queue:** §2.1. `.gitignore:23-24` verified — the queue is never in a clone, so any consumer must treat its absence as normal, and no consumer may treat its absence as "no work."
